# 転載ドリップ効果測定ループ — 設計

- 日付: 2026-10-25
- 承認: ふくけい（会話内設計承認済み・Zenn取得方式変更も承認済み）
- 起因: ふくけい「既存の車輪に比して、劣っているところは？」→ CC の自己評価「効果測定ループなし」→ ふくけい「効果測定ループの設計に入って」
- ゴール: **集計+週次報告**（改善判断は人間）・測定対象 **note+Zenn**・報告先 **SSOT日記+Discord**

## ⚠️ 方式変更（2026-10-25 23時・ふくけい承認）: Zenn取得は「CC取得方式」

- Python playwright での Zenn ログインが Cloudflare に拒否（素の headed も stealth 適用版も拒否・ふくけい操作でもはね返される実測）
- **変更後**: Zenn の数値は **CC が MCP Playwright（ログイン済みプロファイル）で統計ページ（zenn.dev/dashboard/stats）を開いて取得**し、metrics.jsonl に追記する
- 取得手順（CC手順書）: ①navigate → /dashboard/stats ②「もっと読み込む」をボタンが消えるまでクリック ③snapshot を filename 保存 ④yml から `link "タイトル"` + `/articles/<slug>` + `text: "N"` + `generic: 回` の組を抽出 ⑤jsonl 追記（重複date+slug は skip）
- **実測済みの限界**: 初回展開で30件取得（全体47本の記事があるが stats の初期表示分のみ=取りこぼしの可能性・週次運用で観察し、増やせる場合はクリック回数を増やす）

## 1. アーキテクチャ

```
【日次 cron】collect_repost_metrics.sh（新設）
  ├─ note: Playwright（repost_note_login.py が維持するログインセッション流用）
  │   → noteダッシュボード（note.com/mypage/contents）→ 転載済み記事のビュー・スキ数
  ├─ Zenn: Playwright → zenn.dev/dashboard/analytics → 転載元記事のビュー数
  │   ※ Zenn は初回のみふくけいの手動ログインが必要（memory: playwright-loggedin-browsing 方式）
  └─ ~/projects/zenn/repost-metrics/metrics.jsonl に追記（1行=1日×1記事・append only）

【週次 cron（日曜）】repost_weekly_summary.py（新設）
  → metrics.jsonl を集計 → 週次サマリ生成
  → SSOT日記（10_DAILY）に追記 + Discord 通知
  → サマリ内容: 記事別ビュー/スキ・転載先(note)vs転載元(Zenn)のビュー比・上位/下位
```

## 2. データ形式

metrics.jsonl（append only・壊れても前日までのデータは残る）:
```json
{"date": "2026-10-25", "slug": "caddy-nginx-replacement-vps", "platform": "note", "note_id": "nb985b0fa3549", "views": 123, "likes": 4}
{"date": "2026-10-25", "slug": "caddy-nginx-replacement-vps", "platform": "zenn", "views": 456, "likes": 12}
```
- 日次差分は集計時（前日行との差）に計算・生値のみ保存
- 取得失敗時はその日の行を書かない（欠損として扱う・0を書かない）

## 3. 記事リストの取得元

`repost-queue.md` の `[x]` 行（note URL 記録済み）から slug・note_id・Zenn URL を抽出（単一正典・キューと測定対象が自然に同期）。

## 4. Phase 0（実現性確認・実装着手前に必須）

1. noteダッシュボードでビュー・スキ数が Playwright で取得できるか実測（セレクタ確定）
2. Zenn analytics 同様に実測（ふくけいの手動ログイン1回を伴う）
3. 両方不可の場合は設計失敗として止め、ふくけいに報告（代替: 手動集計テンプレ）

## 5. cron

- 日次収集: 既存 drip cron（cron-id:32/33）の時間帯と被らないスロット・flock+当日スタンプ（cron-setup 規定路線準拠）
- 週次レポート: 日曜朝（Daily Triage 後の空きスロット）
- 排他設計・renew-crons.sh 追記・apply-crons reconcile は cron-setup スキルの手順に従う

## 6. 検証

- collect スクリプト: 単体（パーサ部分）+ 実取得1回（Phase 0 で確定したセレクタ）・EXIT で成功/失敗判定
- summary スクリプト: テストデータ（fixture jsonl）で集計ロジック検証+実データ1回
- fail条件: 週次サマリが2週連続で生成されなかった時（cron 失敗の検知は Discord 通知の不在としても視認）

## 7. スコープ外（明示）

- タイトル/カバーの自動調整（2段階目・データ貯まってから別設計）
- 他プラットフォーム（Qiita は429頻発のため対象外）
- X 連携等のシェア数測定
