## はじめに

LLMにコード修正を任せていると、一度は必ず遭遇するのが「指示していない行まで消される」事故です。1関数の修正を頼んだだけなのに、気づけばファイルの半分が「リファクタリング」という名の破壊されていた――。自律コーディングエージェントを開発していると、こうした失敗は日常茶飯事です。

私が開発しているNexusCoreには、複数のLLMに実際の修正タスクを投げて成功率を測る「nexuscore-bench」というベンチマークがあります。検証で判明した失敗パターンを「壁」と名付けて1つずつ潰しているのですが、そのうちの**壁2-A「過剰削除」**への対策として実装したのが**削除行数上限ガード（max_delete_lines=20）**です。

この記事では、その設計思想とPython実装、そしてガード単体では不十分な理由まで解説します。

## 事故の実態：LLMはなぜ関係ない行を消すのか

nexuscore-benchでは、GLM・Gemini・MiniMaxなど複数のモデルに同一タスクを与え、パッチ生成→適用→テスト実行までのフルループを検証しています。そこで観測された過剰削除には、大きく2つのパターンがありました。

**パターン1：勝手な「ついでリファクタリング」**
エージェントの学習経路（経験をコード改善に活かすパイプライン）の1関数を直すタスクで、モデルが対象の修正に加えて「コードを整理した」と称してファイルの広範囲を削除。修正自体は合っていたのに、依存コードが壊れてテストが真っ赤になりました。

**パターン2：diff形式で回答してくる**
プロンプトで「完全なソースを返せ」と指示しても、diff形式で返してくるモデルがあります。これを雑にパースして適用すると、余計な行まで消えます。実際には「diff回答も元ソースへの適用で完全なソースを再構成する」修正で対処しました。

重要なのは、これらが特定モデルだけの問題ではないことです。どのモデルでも確率的に起きるため、**プロンプトで抑え込むのではなく、システム側で物理的に防ぐ**必要がありました。

## 実装：difflibで削除行数を数えるシンプルなガード

ガードの本体は驚くほどシンプルです。旧ソースと新ソースを`difflib`で比較し、削除行数が上限を超えていたら例外で適用を阻止します。

```python
import difflib

MAX_DELETE_LINES = 20


class TooManyDeletionsError(Exception):
    """削除行数が上限を超えたときに発生する例外"""


def count_deleted_lines(old_source: str, new_source: str) -> int:
    """旧ソース→新ソースの比較で、削除された行数を返す"""
    old_lines = old_source.splitlines(keepends=True)
    new_lines = new_source.splitlines(keepends=True)

    deleted = 0
    for line in difflib.unified_diff(old_lines, new_lines, n=0):
        # hunkヘッダ(@@)と追加行(+)を除外し、削除行(-)だけを数える
        if line.startswith("-") and not line.startswith("---"):
            deleted += 1
    return deleted


def enforce_delete_limit(old_source: str, new_source: str) -> None:
    """削除行数が上限を超えていたら例外で適用をブロックする"""
    deleted = count_deleted_lines(old_source, new_source)
    if deleted > MAX_DELETE_LINES:
        raise TooManyDeletionsError(
            f"削除 {deleted} 行が上限 {MAX_DELETE_LINES} 行を超過。"
            "意図しない大規模削除の疑いがあるため適用を中止します"
        )
```

設計上のポイントは3つです。

1. **適用前に検証する**。ガードはパイプラインの「生成後・適用前」に挿入します。壊れたコードがディスクに書き込まれる前に止まるので、被害がゼロで済みます。
2. **`n=0`でコンテキスト行を切る**。`unified_diff`はデフォルトで前後3行のコンテキストを含みますが、行数カウントには不要なので`n=0`にします。
3. **上限はタスク設計から決める**。ベンチのタスクで想定される変更は数行〜十数行なので、20行超の削除は「タスクの範囲外」と判断できます。この数字はプロジェクトごとに調整すべき値です。

## ガード単体では足りない：多層防御の一部として組み込む

削除行数ガードはあくまで「量」のチェックです。20行以内の削除でも構文は壊れ得ます。そこでNexusCoreでは、このガードを複数の安全機構の一部として配置しています。

- **diff回答の再構成**：モデルがdiffを返したら元ソース適用で完全なソースを組み直す
- **コードフェンス抽出の堅牢化**：説明文の混入でSyntaxErrorになる事故に対し、抽出ロジック自体を修正
- **AST安全検証とロールバック（壁2-B）**：適用後にASTレベルで検証し、不正なら自動で巻き戻す
- **sandbox出力ログ**：検証失敗時にログを残し、原因を事後追跡可能にする

「行数ガードで明らかな暴走を止め、AST検証で細かい破壊を止め、ロールバックで最後の砦を張る」。1つの仕組みに頼らず薄い防御を重ねるのが、LLM駆動開発を安全に回すコツだと実感しています。

## おわりに

削除行数上限ガードは、実装すれば30行足らずのシンプルな機構です。しかしこれらの防御を積み重ねた結果、nexuscore-benchのフルループ検証は4/4成功まで到達できました。LLMの能力向上に頼るだけでなく、副作用を物理的に封じる小さなガードを積み重ねる――それがLLM駆動開発を継続的に回す現実的な道筋だと考えます。

みなさんのプロジェクトでも、LLMにコードを触らせる前に「削除される行数の上限」を決めておくことをおすすめします。
