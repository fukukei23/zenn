## はじめに

Claude Codeを使った日々の開発の中で、**multi-llm-review（以下、MLR）**――同じコードを複数のLLMにレビューさせる仕組み――を自作して運用しています。

今回はそのMLR自体の品質改善の全記録をまとめます。5機（5モデル）のレビューで集まった25件の指摘を統合し、17本のテストを追加して**全349テスト緑**に到達するまでの過程で学んだ、「フォールバック設計の実践知」を共有します。

- provider動的検知と `served_model` 照合
- 並列レビュー枠（or_slots）の段階的昇格
- 実APIを叩かない決定的テストの書き方

## 1. 5機25指摘――「レビュアー自身をレビューする」

MLRの基本構造はシンプルです。

1. レビュー対象のdiffを用意する
2. 5つのLLMに並列でレビューを依頼する
3.返ってきた指摘を重複統合して1つのリストにする

単一モデルだと「そのモデルの得意領域の外」は見逃されがちですが、複数機で回すと互いの穴を埋め合います。実際、別コンポーネントの変更をレビューしたところ25件もの指摘が集まり、権限昇格経路の遮断（root所有の実行コピー化）といった重大な修正につながりました。

そこで発想を転換し、**「レビューする側＝MLR自身をレビューにかける」メタレビュー**を5機×複数ラウンドで実施したところ、MLR v3.0自体にこんな穴が出てきました。

- providerを設定ファイル上の名前で固定判定していた（実態とズレうる）
- 一部providerのログ経路が未整備で、障害時に追跡不能
- 期待するprovider構成が揃っていなくてもレビューが開始されてしまう

## 2. 実効provider動的検知――設定名を信用しない

プロキシ経由でLLM APIを利用していると、**設定上の名前と実際に応答するモデルがズレる**ことがあります。aliasやフォールバックが挟まるためです。「GLMのつもりでレビューしてもらっていたら別モデルだった」では、レビュー品質の記録がすべて崩れます。

そこで、応答に含まれる `served_model`（実際に応答したモデル名）と期待値を照合し、実効providerを実行時に判定するようにしました。

```python
EXPECTED_SERVED = {
    "glm": "glm-",       # 前置一致でバージョン違いに耐える
    "minimax": "MiniMax-",
}

def detect_effective_provider(resp: dict, configured: str) -> str:
    """設定名ではなく応答実体から実効providerを判定する"""
    served = resp.get("served_model", "")
    if served:
        for provider, prefix in EXPECTED_SERVED.items():
            if served.startswith(prefix):
                return provider
    # 判定不能でもクラッシュしない: unknownへ落として警告ログに出す
    return "unknown"
```

さらに**policy起動ゲート**を追加しました。レビュー開始前に「実効provider構成が期待どおりか」を検査し、不足があれば開始をブロックして警告を出します。これで「壊れた構成のまま薄いレビューが通ってしまう」事故を防げます。

フォールバック設計の原則として意識したのは次の3点です。

- 判定不能は `unknown` に落とし、クラッシュせずログで警告する
- 実行中に一部providerが欠けても、他providerのレビューは継続する
- ただし「開始時点で欠けている」ことはゲートで止める（静かな劣化を許さない）

## 3. or_slots 2→3昇格とテスト拡充――実測データによる段階導入

or_slotsは並列レビューの枠数です。いきなり増やすとレート制限やタイムアウトで逆に欠員が増えます。そこで仕様書に昇格条件を先に書いておきました。

- 欠員率 < 30%
- 1レビューあたり10分超過が0件

初週の実測は**欠員率約19%、10分超過0件**。条件を達成したので2→3へ昇格しました。この「閾値を先に決め、実測で判定してから一段階ずつ上げる」進め方は、LLM関連のパラメータ調整全般に応用できると感じています。

テストは17本追加しました。ポイントは**実APIを叩かず、応答オブジェクトをスタブ化した決定的テスト**にすること。ネットワーク状態にテスト結果が左右されません。

```python
def test_detect_by_served_model_not_config():
    resp = {"served_model": "MiniMax-M2"}
    # 設定名が間違っていても、応答実体で正しく判定される
    assert detect_effective_provider(resp, "glm") == "minimax"

def test_unknown_falls_back_safely():
    resp = {"served_model": "totally-unknown-model"}
    # unknownに落ちても例外を投げない
    assert detect_effective_provider(resp, "glm") == "unknown"
```

追加したテストの対象は、provider検知のパターン網羅（一致・不一致・`served_model` 欠落）、各providerのログ経路、起動ゲートの通過・ブロックです。結果、**全349テストが緑**になりました。

## おわりに

今回の穴塞ぎで得られた教訓は次の3つです。

1. **メタレビューが効く**: レビューツール自身をレビューにかけることで、使い手が気づけない穴が見つかる
2. **設定でなく実体を検知する**: aliasやフォールバックが存在する環境では、応答実体（`served_model`）だけが信頼できる
3. **並列度は実測で段階的に上げる**: 閾値を先に決めて実測がクリアしたら昇格、という運用が安定する

349緑はゴールではなく通過点です。provider構成や仕様が変われば、テストもゲートも追従していく必要があります。マルチLLMレビューの設計に取り組んでいる方の参考になれば幸いです。
