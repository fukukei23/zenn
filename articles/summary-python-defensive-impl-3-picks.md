# はじめに

プログラムが「大きなエラー音を立てて」壊れるうちは良いのですが、厄介なのは**誰も気付かないうちに静かに壊れている**パターンです。この記事は、私が実際に踏んだ3つの「静かな破壊」——**環境変数が届かない・LLMが関係ない行を消す・特定の文字だけで保存が死ぬ**——への防御実装をまとめたものです。

共通するテーマは「**エラーに頼らず、構造で防ぐ**」です。

# 1. 環境変数はプロセスの国境を越えない —— argv明示渡し

WSL上のスクリプトをWindows側のフック経由で起動したとき、セッションID（SID）が空になり、ログのセッション紐付けだけが**エラーも出さずに**壊れていました。

原因は、環境変数がプロセスの境界を越えて伝播しないことです。WSLとWindowsのように異なる実行環境の間では、親でexportした変数が子に渡らないケースがあります。WSLのbashで `.env` を export しても、Windows側プロセスから起動されたスクリプトには届きません。

```python
# 壊れていた書き方: 空文字のまま静かに進む
sid = os.environ.get("SID", "")

# 修正後: argvで明示的に渡す（無ければエラーで落とす）
sid = sys.argv[sys.argv.index("--sid") + 1]
```

**設計の判断ポイント**は「黙ってデフォルト値に逃がさない」ことです。`os.environ.get(..., "")` は便利ですが、**必須の値には使わない**——無ければ例外で落とすほうが、壊れたログが量産されてから気付くよりずっと安上がりです。どうしても環境変数を使う場合も、`WSLENV` 等の明示的な橋渡し設定を「設定ファイルに書いてレビューに残す」運用にしています。

# 2. LLMの暴走削除はプロンプトではなく、システムで物理的に防ぐ

LLMにコード修正を任せていると「指示していない行まで消される」事故が起きます。複数モデルに同一タスクを投げるベンチマークを運用したところ、過剰削除は**どのモデルでも確率的に発生する**ことが分かりました。

対策として実装したのが**削除行数上限ガード（max_delete_lines=20）**です。

```python
def check_delete_limit(patch_lines: list[str], max_delete: int = 20) -> None:
    deleted = sum(1 for l in patch_lines if l.startswith("-") and not l.startswith("---"))
    if deleted > max_delete:
        raise ValueError(f"削除{deleted}行が上限{max_delete}行を超過")
```

ポイントは、**この1個のガードを最終手段にしない**ことです。ガードをすり抜ける書き方（diff回答の雑なパース等）が別途見つかったため、最終的には「diff回答を元ソースに適用して完全なソースを再構成する」という入力段階の正規化と組み合わせて、はじめて実用になりました。プロンプトで「消さないで」と頼むのは設定ではなく希望です。

# 3. 孤立サロゲート —— strのままでは気付けず、保存で爆発する

外部コマンドの出力をログに保存するタスクロガーで、**特定のタスクのログだけ**保存に失敗する現象が起きました。エラーメッセージはこれです。

```
UnicodeEncodeError: 'utf-8' codec can't encode character '\udc80': surrogates not allowed
```

原因は**孤立サロゲート（ペアを失ったUTF-16の片割れ）**です。厄介なのは、Pythonの `str` はこれを**エラーなしに保持できる**こと。文字列を受け取った時点では何も起きず、`encode("utf-8")` が走った瞬間に初めて爆発します。しかも保存が死ぬので、そのログ自体が失われる二次被害まであります。

対策は、保存前の無害化関数です。

```python
def sanitize_for_utf8(text: str, errors: str = "replace") -> str:
    """孤立サロゲート等を無害化してUTF-8保存可能にする。"""
    return text.encode("utf-8", errors=errors).decode("utf-8")
```

TDDで「赤→緑」を回すと、**失敗するケースを先にテストとして固定できる**のが利点です。「外部コマンド出力をそのままstrにするな」「保存前に1回encode/decodeで丸める」は、ログ系ツールを書くときの定番の防御姿勢になりました。

# おわりに —— 「静かに壊れる」への3つの防御姿勢

| 事故 | 防御 |
|---|---|
| 環境変数が届かない | 必須値は黙ってデフォルトに逃がさない（argv・例外） |
| LLMの暴走削除 | プロンプトでなくシステムで物理的に防ぐ（複数の層で） |
| 孤立サロゲート | 境界（外部入力・保存前）で1回丸める |

3つに共通するのは、**エラーが起きてから対処するのではなく、エラーが起きない構造を先に作る**ということでした。「静かに壊れる」箇所は、ログが途切れる・空文字がそのまま記録される・特定のデータだけ保存に失敗する、という小さな異変が唯一のサインです。異変に気付いたら、その奥に同じ型の事故が眠っていないか、一度見直してみてください。
