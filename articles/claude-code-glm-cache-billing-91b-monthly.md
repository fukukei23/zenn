## はじめに

前回の記事（[Claude Code CLIをGLM（Z.AI）で代替した話](https://zenn.dev/fukukei23/articles/claude-code-cost-optimization)）では、Claude CodeのバックエンドをGLMに差し替えてコストを削減した話を書きました。その後さらに運用を続け、月間9.15B（**91.5億**）トークンという使用量に達しました。ダッシュボード表示の累計では37.2B（372億）トークン・120日連続の毎日使用です。

この記事では、その規模に達したときに初めて見えてきた**キャッシュ課金の罠**と、**週間制限に現実的に到達する使用量の実態**、そして**文脈肥大対策の運用**を、実際のダッシュボード数値とともにまとめます。

Claude CodeのAPIコストに悩む方、サブスクリプションの「20x」が実際にどれくらい使えるのか気になっている方の参考になれば幸いです。

## 構成: Claude Code → 自作プロキシ → GLM

構成は前回記事と同じです。

```
Claude Code CLI（設定はそのまま）
    ↓ localhost:8787
自作プロキシ（glm-rate-proxy・WSL内で常駐）
    ↓ 使用率に応じてルーティング
Z.AI API（GLM-5.3 / GLM-5.3-Flash）
```

Claude Code側は公式のCLIのまま、接続先だけを自作プロキシに変更します。このプロキシがZ.AI APIへリクエストを転送します。使用率が高まったときのモデル切替（Flashへのフォールバック）もプロキシが担います。

契約はZ.AIの **GLM Coding Max-Quarterly Plan（Legacy Plan V2・$216/四半期）**。月額換算で **$72**、Lite比20xの使用枠です。なお本記事の「$72」は**この固定枠の契約額**を指し、枠内で処理した実使用量の話です（枠を超えた分の追加従量課金は発生していません）。

## コスト比較: 月91億トークンの実績を各プランで計算すると

まず、私の実際の使用量です（2026年10〜11月期・Z.AIダッシュボード実測・各数値の集計窓は表示時に準拠）。

| 項目 | 実測値 |
|---|---|
| 月間トークン（30日窓） | **9.15B（91.5億・30日平均305.05M/日）** |
| 日別ピーク | **1.04B（10月27日の1日）** |
| 累計トークン / 連続使用日数 | 37.2B / **120日連続** |
| キャッシュヒット率（30日窓） | **95.1〜95.8%** |
| 月額コスト | **$216/四半期 = $72/月相当（固定）** |

この「月91億トークン」を、同じ期間で他のプラン・従量課金で使ったらいくらになるかを計算したのが次の表です。トークン構成は、30日窓のダッシュボード実測値（**キャッシュ読み取り約95.5%・通常入力約4%・出力約0.3%**）を使い、各社の公表価格に当てはめた**概算**です。

| 方式 | 月額相当 | 私の実績との比 |
|---|---|---|
| **GLM Coding Plan（私の実績）** | **$72固定** | 1倍 |
| Claude API従量・Sonnet換算 | 約$1,880/月 | **約26倍** |
| Claude API従量・Opus換算 | 約$3,760/月 | **約52倍** |
| Claude Max 20x（$200/月） | $200固定 | 約1/2.8の価格・ただし容量に問題（後述） |

換算に使った価格は、**Claude Sonnet 5.5**（入力$2/M・キャッシュ読み$0.10/M・出力$10/M）と**Claude Opus 5.5**（入力$4/M・キャッシュ読み$0.20/M・出力$20/M）の公表価格（2026-11-10・platform.claude.com公式確認）に上記トークン構成を当てはめた概算です（倍率は$1,880÷72≒26倍・$3,760÷72≒52倍という計算に基づきます。なお旧世代モデル〔Sonnet 4.5級： 入力$3/キャッシュ$0.30/出力$15・Opus 4.1級： 入力$15/キャッシュ読み$1.50/出力$75〕で計算すると約$4,250/月＝約59倍・約2.4万ドル/月＝約330倍となり、モデル世代で倍率が大きく動く点にご注意ください）。

重要なのは「**モデルの性能が同等という前提での比較ではない**」ことです。私の日常運用はGLM-5.3-Flash（高速・低価格モデル）で、Claudeのモデル対応で言えばSonnet寄りの立ち位置です。同じ性能帯（現行Sonnet級）で比べた場合が「約26倍」です。性能比較（コード品質・遅延等）は本記事のスコープ外です。なお、日常のリクエストのトークン内訳はキャッシュ94.8%・非キャッシュ4.7%・出力0.2%という実測（2026-11-10の1日分）で、ほぼすべてが「キャッシュ読み取り」で占められているのがClaude Code利用の実態です。

### Claude Max 20x（$200/月）は容量として足りるのか

コストだけならGLMの優位は明らかですが、「じゃあ純正のサブスク（月額固定）で済ませられないか」という視点も大事です。そこでClaude Max 20x（$200/月）の実態を調べました。公式は「Pro比20倍・5時間あたりの制限」しか明示しておらず、**週間上限の具体的数値は非公開**です。

コミュニティの実測報告（Reddit r/ClaudeCode・r/ClaudeAI等の複数スレッド・2026年11月時点の確認）では:

- 「Max 20xの週間制限を**1日足らずで**使い切った」という報告
- 「20xは週次・月次で20倍ではない」という指摘
- 「Max 20xはMax 5xの実質**約1.5倍**しか使えない」という計測報告

※これらはコミュニティ報告であり公式仕様ではありません。利用条件やモデル構成によって変わる可能性があります。

つまり月$200でも、フルタイムに近いClaude Code利用では週間制限に到達するリスクが高いのが現状です。後述するように、私自身もGLMの週間制限（GLM側にも週間枠はあります）に3日間到達した経験があるので、「週間制限に当たったら作業が止まる」という問題自体はどちらのプロバイダーでも起こり得ます。

## キャッシュ課金の罠 — 96%キャッシュヒットなのに枠の消費が急速に進む理由

ここが本記事の核心です。Claude Codeの利用では、キャッシュヒット率が90%台後半に達するのが普通です。直感では「キャッシュが効いているからコストは抑えられるはず」と思います。ところが実際には、**キャッシュヒットした分も課金される**という構造があり、その割引率はプロバイダーによって大きく違います。

| プロバイダー | キャッシュ読み取りの課金 |
|---|---|
| Anthropic API（公式価格） | 通常入力の**約1/10** |
| Z.AI API従量課金 | 通常入力の**約1/5**（GLM-5.3-Flash: 入力$0.15 → キャッシュ$0.03・2026年11月時点の公式料金表） |
| Z.AI Coding Plan（2026-07-30以降のクレジット制） | 乗数0.56倍（公式クレジット式） |

つまりAnthropicなら「キャッシュヒット分は1割」と軽いのですが、Z.AIでは**クレジット制で約56%（0.56倍）・API従量で約20%（1/5）**が課金されます。キャッシュヒット率95%の利用では、**総トークンの約95%をキャッシュ読み取りが占める**（ダッシュボード実測）ため、キャッシュが効いていても枠の消費が大きく膨らみます。

### 私が「フルカウント」と誤解した経緯と、数値検証

この構造を理解する前、私は「Z.AIはキャッシュ読み取りをフルカウントするのではないか」と仮定して調査しました。週間枠の23%が4時間程度で消費された事例（後述）が、キャッシュ割引なしの計算としか整合しなかったからです。

しかし公式ドキュメントの確認とダッシュボード実測値の突合で、この仮定は誤りと分かりました:

- 公式料金表でキャッシュ入力単価（約1/5）を確認
- 公式のクレジット計算式でキャッシュ乗数0.56倍を確認
- 実測値の突合: 直近7日の使用量935.1Mトークン（ヒット率95.8%）を公式の週次許容量表（ヒット率96%・Max枠=2,101〜4,202M）に当てると **935.1 ÷ 4,202 = 22.3% ≈ ダッシュボード表示23%** と定量一致（もしフルカウントなら同じ使用量が週間枠の約1.5倍に相当する計算となり、23%表示と矛盾する）

「キャッシュが効いていても課金される」は正しいですが、「フルカウント」ではありません。**10%ではなく56%が課金される**、が正確な理解です。

### 並行セッションでキャッシュが壊れる問題

さらに厄介なのが、キャッシュそのものの挙動です。Z.AIのコンテキストキャッシュは**同一APIキーで共有される**ため、並行セッションが走ると互いのキャッシュエントリを追い出し合います（「キャッシュプールが綱引き状態になる」と表現した第三者の詳細な実測報告があります・deepseek-harnessのGitHub Discussion #5227・GLM-5.3-Flashの実ログ解析・2026年11月参照）。prefix（会話の先頭部分）が不変でも完全ミスが発生し、キャッシュ崩壊時は実質2〜3倍の消費になるとの報告です。※これは第三者の実測であり、私の環境での独立検証はまだです。

私の環境では、メイン作業のClaude Codeセッションに加えて、夜間の定期処理や複数タブの並行作業が同じAPIキーで動くため、この綱引きは常に起こり得ます。

## 週間制限の実態: Legacy V2 Max（20x）でも3日間到達した

私の実績から、週間制限の現実的な姿を共有します。

直近7日の使用量が「935.1M（日平均133.59M・前期比-69%※ダッシュボード表示値）」と一見減少して見えました。しかし内訳を確認すると、**この7日のうち3日間は週間制限に当たって使用できなかった日**でした。つまり「減少」ではなく「使えなかった」です。

1か月平均の305.05M/日が通常運用の実態で、GLM Coding Planの上位枠（20x）でも**週間制限に到達する使用は現実に起こる**ということです。たとえば複数の大きなリポジトリを同時に並行作業していると、1セッションあたりの文脈が肥大し、週間枠を急速に消費します。

実際に起きた事故として、**文脈が60〜72万トークンまで成長したセッションが3本**並行していたことがあり、この状態での毎ターンの再送信だけで、4時間程度で週間枠の大半を消費しました（当日の使用量は約718M・キャッシュ読み取りが96%以上という実測）。キャッシュヒットしていても「0.56倍換算×巨大な文脈」は重い、というのが本質です。

## 文脈肥大対策: 消費を約1/3.5に抑える見込み

この事故を機に、運用と機械化の両面で対策を入れました。

### 運用: 「日をまたぐら new-session」

Claude Codeのコンテキストは、セッションを続けるほど肥大します（システムプロンプト＋会話履歴＋ツール結果が毎ターン全文再送される）。そこで運用ルールを1つ決めました。

> **作業をまたいで日が変わる時点で、必ず new-session で引き継ぐ**

引き継ぎにはセッションの要約・未解決タスク・参照ファイルを自動生成するスクリプトを使っているため、文脈を失わずに新しいセッションへ移れます。この運用で、セッションの文脈が自然に20〜25万トークン程度に収まり、**消費量は約1/3.5に減る**と見積もっています（作業増分は1日約10万トークン、新セッションの固定コストは約11万トークンという実測に基づく計算・※まだ本格運用前の見込み値です）。

なお「日をまたぐら」としたのは、もっと短い間隔で区切ると引き継ぎコスト（固定コスト+要約生成）が相対的に重くなるためです。**区切りすぎの悪循環**には注意が必要です。

### 機械化: context-size-warn hook

運用だけでは「巨大化に気付けない」ので、Claude CodeのPostToolUse hookで自動監視も入れました。

| 項目 | 設定 |
|---|---|
| 警告閾値 | 25万トークン超 |
| 再警告 | 5万トークン増分ごとに1回（アラート疲労対策） |
| 強警告 | 50万トークン超 |

セッションのコンテキストサイズが閾値を超えるとターミナルに警告が表示されるため、「気づかずに巨大セッションを運用し続ける」事故を構造的に防げます。

### さらに検討中: cache_control注入

調査過程で、Z.AIの互換エンドポイントがAnthropic形式の`cache_control`パラメータを受け付けることが、前述の第三者の実測報告（同GitHub Discussion）で判明しました。これを注入すると、報告者環境ではターンレベルのキャッシュヒット率が70.5%→86.9%に改善したというデータがあります。※第三者の実測であり、私の環境での再現性は未検証です。私のプロキシへの実装は今後の検討課題です（プロキシはセッション共有の常駐プロセスなので、変更時は全セッションが数秒止まるため、注意深くやる必要があります）。

## まとめ

- Claude CodeのバックエンドをGLMに差し替え、月91億トークンを**$72の固定枠**で処理している。同等のトークンを現行Claude Sonnet 5.5のAPI従量で使うと約26倍（約$1,880/月相当・概算換算）
- Claude Max 20x（$200/月）は、コミュニティ報告ではヘビー利用で週間制限が1〜3日で到達する事例が複数あり、「月額固定＝使いたい放題」ではない
- **キャッシュヒット分も課金される**点が本質。割引率はプロバイダーで違い、Anthropic=1/10・Z.AI従量=1/5・Z.AIクレジット制=0.56倍。「96%キャッシュヒット」でも枠の消費は急速に進む
- さらに同一APIキーの並行セッションでキャッシュが崩れる問題があり、実質2〜3倍の消費になり得る（第三者の実測報告）
- 対策は「**文脈を小さく保つ**」（日をまたぐら new-session・消費約1/3.5への削減を見込み）＋「**巨大化の自動監視**」（hook自作）が有効
- 使用量が大きい場合、プロバイダーの週間制限に当たるのはGLMでも純正でも起こり得る。制限の数値が明示されているかどうかは、計画を立てるうえで大きい

Claude Codeの利便性を保ったままコストを大きく（本記事の実測では現行Sonnet従量換算の約1/26に）抑える構成は、個人開発者の範囲で十分実現可能です。ただし「差し替えれば解決」ではなく、**キャッシュ課金の構造と文脈肥大の理解**があって初めてコストが制御できる、というのが半年以上の運用を通じた実感です。
