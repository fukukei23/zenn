## はじめに

複数のAIエージェントが協調して動くシステムはとても魅力的ですが、開発が進むにつれて「誰がどこを呼んでいるのか」「どのモジュールがもう使われていないのか」が分かりにくくなりがちです。

私が開発・保守を行っている「NexusCore」というリポジトリでも、12のエージェントが複雑に絡み合うパイプラインを実装していく中で、使われないエントリポイントや古い処理がコードベースに沈殿していく課題に直面しました。

今回、NexusCoreの「Stage 3」という開発フェーズにおいて、**未完成のエントリポイントや未使用モジュールの大規模な棚卸し（お片付け）**を行いました。この記事では、その具体的な実例から、コードベースの保守性を維持するための判断基準やリファクタリングの手順をわかりやすく共有します。

## 1. 「抜け殻」と「デッドコード」を斬る勇気

システムを大きくリファクタリングしていると、過去の遺物が残りやすくなります。今回の棚卸しで真っ先に手をつけたのは、**「すでに統合が終わっているのに残っているモジュール」**と**「絶対にエラーになる未完成モジュール」**の削除です。

例えば、かつて存在したメインUI用のファイルは、別の統合UI（`unified_gradio_ui.py`）へ機能が移管された後も、長らく「抜け殻」として残っていました。また、開発ツールとして作成されたマネージャークラスは、内部で**存在しないモジュールを`import`しており、呼び出せば確実に`ImportError`になる**状態でした。

これらを残しておくと、新しい開発メンバーやAIエージェント自身が「どちらのUIを使えばいいんだ？」「このマネージャーを使ってみよう（→動かない！）」と混乱を引き起こします。

### 判断基準：到達可能性と依存関係

削除の判断基準はシンプルです。コードベース全体を検索し、**「どこからもimportされていない」「呼び出そうとするとエラーになる」**ファイルは容赦なく削除します。

「いつか使うかもしれない」という理由でデッドコードを残すのは、保守性を下げるだけです。Gitなどのバージョン管理システムがあるのだから、過去のコードは歴史として残し、現役のコードベースは常にクリーンに保つのが正解です。

## 2. 「静かな失敗」を許さない明示的な設計

未使用モジュールの削除と並んで重要なのが、**「Silent Failure（静かな失敗）」の解消**です。

12のエージェントが協調するシステムでは、一部のエージェントが使用不可になっても、システム全体が止まらないようにフォールバック（代替処理）を行うことがあります。しかし、単に空のデータを返して「正常終了」させてしまうと、開発者は「エージェントが正常に動いている」と勘違いしてしまいます。

今回のリファクタリングでは、LLM（大規模言語モデル）の呼び出し処理において、実APIが無効な場合に無言でスタブ応答（ダミーデータ）を返す仕様を改修しました。

### Pythonコード例：明示的な警告の実装

単に空の文字列を返すのではなく、`warnings`モジュールやログを使って「これは本来の動作ではない」と明示的に開発者へ通知するようにします。

```python
import warnings
import logging

# ロガーの設定
logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

def call_llm_api(prompt: str, use_real_api: bool = False) -> str:
    """
    LLM APIを呼び出す関数（リファクタリング後）
    """
    if not use_real_api:
        # 無言でスタブを返すのではなく、明示的に警告を出す
        warnings.warn(
            "Real LLM API is disabled. Returning stub response.",
            stacklevel=2
        )
        logger.warning("LLMの実API呼び出しが無効化されています。スタブ応答を返します。")
        return "This is a stub response."
    
    try:
        # 実APIの呼び出し処理
        response = request_external_api(prompt)
        return response
    except Exception as e:
        # エラーを握りつぶさず、ログに残す
        logger.error(f"LLM API call failed: {e}")
        raise
```

このように「動かないなら動かないで、なぜ動かないのかを明示する」ことで、エージェント間の連携がうまくいかない時のトラブルシューティングが格段に楽になります。

## 3. リンターツールと日々の小さなメンテナンス

大規模な機能削除やエラーハンドリングの改善と合わせて、今回のリポジトリでは細かなリファクタリングを多数実施しました。

具体的には以下のような作業です。

- **未使用importの除去**: 使われていないライブラリのインポートを削除
- **型アノテーションの付与**: 引数や戻り値の型（`base_dir: str` など）を明記
- **命名規則の統一**: モデル名の表記揺れ（`minimax-m3` → `MiniMax-M3`）の是正

これらは一見地味な作業ですが、12エージェントが協調するような複雑なシステムでは、**「型のズレ」や「表記の揺れ」が致命的なバグを生む**ことがあります。例えば、環境変数（`.env`）では `MiniMax-M3` と定義されているのに、コード内のデフォルト値が `minimax-m3` になっていると、API呼び出し時に弾かれてしまうのです。

### 保守性の心得：CIに頼る

これらの「小さなズレ」を人間の目だけで防ぐのは困難です。Pythonであれば、`Ruff` や `mypy` といった静的解析ツールをエディタやCI（継続的インテグレーション）に組み込み、コードを書くたびに「未使用のimportがある」「型が違う」と機械的に指摘してもらう仕組みが重要です。

## おわりに

12エージェント協調という複雑なシステムを健全に動かし続けるためには、機能を追加することと同じくらい、**「不要なものを削ぎ落とすこと」**が重要です。

今回のNexusCoreの棚卸しを通じて得た保守性の心得は、以下の3点に集約されます。

1. **デッドコードは迷わず削除する**（バージョン管理システムを信頼する）
2. ** Silent Failure（静かな失敗）を作らない**（フォールバック時には明示的な警告を出す）
3. **リンターや型ヒントを活用し、表記揺れを防ぐ**

「まだ動くからいいか」と放置した負債は、システムが大きくなるほど解体できなくなります。みなさんのコードベースにも、もし手つかずの「未完成エントリポイント」や「使われていない謎のモジュール」が眠っていたら、ぜひ今回の記事を参考に一度棚卸しを行ってみてください。きっと今後の開発スピードが大きく向上するはずです。
