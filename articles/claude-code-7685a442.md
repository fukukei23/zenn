## はじめに

Claude Codeに社外向けメールの下書きを作成させて運用している方、多いのではないでしょうか。私も自分用の設定リポジトリに「外向き返信（outward-reply）」用のガードレールを構築し、日々運用しています。

最初に作ったのは「最小禁止リスト」——書いてはいけない表現を列挙する方式でした。ところが運用を重ねるうちにリストは9項目まで膨らみ、それでも穴が埋まらない。最終的に「ネイティブビジネス感覚チェック」という5観点の点検方式へ設計を転換しました。本記事では、この「禁止列挙 → 観点ベース」の進化の実録を解説します。

## 1. 禁止列挙型ルールが脆かった話

### モグラ叩きになる

初期のガードレールは「こう書くな」の列挙でした。実際、運用中の事故のたびに項目が増えていきました。

- **時制の虚偽**：まだ完了していない作業を「完了しました」と書いた事故 → 進行形/完了形の事実整合チェックを追加
- **機能の虚偽**：未実装の機能を実装済みのように書いた事故 → 「実証済・見込み・未実装」の状態判定を追加
- **自己宣言型敬語**：「誠実にお伝えしますと」のような不自然な前置き → 定型表現への置換規則を追加

つまり**禁止リストは「一度起きた失敗」にしか効きません**。起きる前に予測できない失敗は、リストに載っていないので素通りします。

### 実際に起きた「リストにない穴」

象徴的だったのが金額の事故です。下書きに「通常2,000円」と書いたのに、過去に決定した価格は15,000円だった——ということが発生しました。禁止リストには「虚偽を書くな」はありましたが、「数字を過去決定と照合せよ」という観点がなかったため、書いた側に虚偽のつもりがなくても、間違った数字が検証なしに通過してしまったのです。

## 2. 転換点：「禁止でなく、感覚を反映して」

### 添削者視点の導入

転機は、出力を添削してくれた人からの一言でした。

> 禁止するのではなく、感覚を反映してはどうか

この指示を実装したのが「ネイティブビジネス感覚チェック」です。「悪い例の列挙」ではなく、**日本語ビジネス文書に精通した添削者が常に持っている5つの観点**を判定軸として常時適用する方式です。従来の禁止語リストのうち自然な敬語に関する項目は、この観点の一部として再位置付けし、丸ごと捨てるのではなく移行しました。

### 観点ベースの強み

運用してみると、次の違いが明確になりました。

- **列挙されていない失敗も拾える**：「〜してはいけない」の有限リストに対し、観点は「良い文とは何か」のフィルタなので、未知の失敗にも届く
- **ルールが増えても軸はブレない**：項目が9個、15個と増えても、判定軸は5観点のまま
- **人間のレビューと同じ軸**：添削者が見るべきところをLLMが見るので、出力の一貫性が安定する

具体例を挙げます。後から追加した観点に「往復内での自側説明の再掲禁止」があります。これは「相手は過去の発言を読んでいる前提で、質問への回答は回答に絞る」という感覚です。すでに説明済みの内容を再度丁寧に説明し直す文は、禁止ワードのリストでは原理的に検出できませんが、「読み手の視点」という観点があれば自然に弾けます。

## 3. 事実系は列挙で守る：ハイブリッド設計

とはいえ、観点ベースにすべてを任せるわけではありません。現在の設計は**トーンや自然さは「観点」、事実性は「列挙＋照合」**と切り分けるハイブリッドです。

数字については「数字の健康診断」というチェックを用意し、そこに「価格・料金はSSOT（Single Source of Truth）の過去決定と照合する」規則を加えました。イメージはこんなコードです。

```python
import re

# 過去に決定した事実の一覧（SSOT）
SSOT_PRICES = {"初期費用": 15000, "月額サポート": 2000}

def check_prices(draft: str) -> list[str]:
    """下書き中の金額をSSOTと照合する健康診断"""
    problems = []
    for m in re.finditer(r"([\d,]+)\s*円", draft):
        amount = int(m.group(1).replace(",", ""))
        if amount not in SSOT_PRICES.values():
            problems.append(
                f"SSOTに未登録の金額: {m.group(0)}（過去決定と照合してください）"
            )
    return problems

draft = "初期費用は通常15,000円、月額サポートは3,000円です。"
print(check_prices(draft))
# ['SSOTに未登録の金額: 3,000円（過去決定と照合してください）']
```

「3,000円」が過去決定に存在しないことを機械的に検出できます。虚偽の意図がなくても起きる数字のズレは、人間の感覚に頼るより単純な照合のほうが確実です。

## おわりに

現在のガードレールは次の3層構成です。

1. **最小禁止リスト**：時制・機能状態など、実際に事故が起きた事実系の列挙ルール
2. **数字の健康診断**：金額等をSSOTと照合する機械チェック
3. **ネイティブビジネス感覚チェック**：添削者視点の5観点を常時適用

禁止列挙は「既知の失敗」に強く「未知の失敗」に弱い。観点ベースはその逆の性質を持ち、両者を組み合わせて初めて実用になる——これが今回の教訓です。LLMに出力を任せ続けるほどルールは増えますが、その増やし方の設計思想次第で、ガードレールは保守しやすくも脆くもなります。同じ悩みを持つ方の参考になれば幸いです。
