# はじめに

自動化スクリプトやバッチ処理を開発していると、「特定のファイルが置かれたら処理を実行する」といったファイルトリガーベースの仕組みをよく作ります。こういった仕組みは手軽で便利な反面、ユニットテスト（単体テスト）を書こうとすると非常に相性が悪いことが多いです。

今回は、自分の管理している設定・自動化用リポジトリで行った `theme_observer` という監視モジュールのリファクタリングを例に、「**依存注入**」の考え方を活用してテスト容易性を爆発的に向上させた具体的な手順を解説します。

「テストが書きにくくて困っている」「依存注入という言葉は知っているけど実務でどう使えばいいかわからない」という方の参考になれば幸いです。

## 密結合なコードが抱える「テスト困難性」の問題

まずはリファクタリング前の「テストが書きにくいコード」の典型的なパターンを見てみましょう。

例えば、監視対象のディレクトリ内に `trigger_file` というファイルが存在するかを確認し、存在する場合はシステムが承認状態（`approved`）かどうかを判定して処理を続行する、といった関数です。

```python
import os
from pathlib import Path

def load_approved() -> bool:
    # 外部ファイルやDBから承認状態を取得する複雑な処理
    # （今回は例として常にTrueを返す）
    return True

def run_observation():
    # 1. トリガーファイルのパスが直書き（ハードコード）されている
    trigger_path = Path("/path/to/specific/trigger_file")
    
    if not trigger_path.exists():
        print("トリガーファイルがありません")
        return
           
    # 2. 外部の関数を直接呼び出している
    if load_approved():
        print("監視処理を開始します")
        # 実際の重いメイン処理...
```

一見すると問題なく動作するように見えますが、このコードには実務上の大きな弱点が2つあります。

1. **ファイルパスのハードコード**: テストを走せるようにするために、本番環境と同じパスに実際にファイルを置く必要があります。
2. **外部関数への密結合**: `load_approved()` がDBアクセスなどを含む場合、このテストを行うためにDBを立ち上げるか、テスト用のDBを用意しなければなりません。

これでは「気軽に回せる高速なユニットテスト」を作ることは不可能です。

## 依存注入（DI）で外部要因を「引数」に切り出す

これらの問題を解決するのが「**依存注入**」という設計手法です。

依存注入と聞くと、JavaのSpring Frameworkのような大規模なフレームワークを想像して難しく感じる方もいるかもしれません。しかし、Pythonにおける基本的なDIの考え方はとてもシンプルです。

**「関数の外側にある環境（ファイルシステム、DB、外部APIなど）にアクセスする処理を、関数の引数として外から渡す」**

たったこれだけです。先ほどのコードにこの考え方を適用してリファクタリングしてみましょう。

```python
from pathlib import Path
from typing import Callable

def run_observation(
    trigger_file: Path,
    load_approved_fn: Callable[[], bool]
):
    """監視処理を実行する関数（リファクタリング後）
    
    Args:
        trigger_file: 監視対象のファイルパス（外部から注入）
        load_approved_fn: 承認状態を判定する関数（外部から注入）
    """
    # 注入されたパスを使用する
    if not trigger_file.exists():
        print("トリガーファイルがありません")
        return
           
    # 注入された関数を使用する
    if load_approved_fn():
        print("監視処理を開始します")
        # 実際の重いメイン処理...
```

変更点は以下の2点です。

1. **`trigger_file` の単体化**: パスを関数の中に固定せず、引数として受け取るようにしました。
2. **`load_approved_fn` の依存注入**: 承認状態を取得する関数を、呼び出し側から渡せるようにしました。

これにより、`run_observation` 関数自身は「どこにあるファイルを読むか」「承認状態をどうやって取得するか」という具体的な実装の責任から解放されました。純粋な「ロジック」だけを担うようになったのです。

## リファクタリング後のテスト容易性が爆上げする具体例

では、実際にこのDIを取り入れたことで、テストコードがどれほど書きやすくなったかを見てみましょう。

Pythonの標準的なテストフレームワークである `pytest` を使って、実際のファイルシステムやDBを一切汚さずにテストを記述します。

```python
import pytest
from pathlib import Path
# リファクタリング後のモジュールをインポート
# from my_module import run_observation

def test_run_observation_no_trigger(tmp_path):
    """トリガーファイルが存在しない場合のテスト"""
    # tmp_pathはpytest組み込みのfixture。一時的な空ディレクトリを自動生成・削除してくれる
    dummy_file = tmp_path / "dummy_trigger"
    
    # 承認状態を返すダミー関数（常にTrueを返す）
    dummy_load_approved = lambda: True
    
    # 実行（実ファイルがなくてもエラーにならず正常系として処理されるか）
    run_observation(
        trigger_file=dummy_file,
        load_approved_fn=dummy_load_approved
    )
    # ここでメイン処理が走っていないことをアサーション等で検証する


def test_run_observation_not_approved(tmp_path):
    """トリガーはあるが、承認されていない場合のテスト"""
    dummy_file = tmp_path / "dummy_trigger"
    dummy_file.touch()  # 実際に空のファイルを作成
    
    # 承認状態を返すダミー関数（今回は未承認を表すFalseを返す）
    dummy_load_approved = lambda: False
    
    # 実行
    run_observation(
        trigger_file=dummy_file,
        load_approved_fn=dummy_load_approved
    )
    # 承認されていないので、メイン処理がスキップされたことを検証する
```

いかがでしょうか。ポイントは `dummy_load_approved = lambda: False` の部分です。
本来であればDB接続などが発生してテストが重くなる「承認状態のチェック」を、`lambda`（無名関数）を使ってその場で簡単にモック（ダミー）化しています。

これにより、以下のような多大なメリットが得られます。

- **超高速化**: ファイルI/OやDB接続がなくなるため、テストがミリ秒単位で完了します。
- **環境非依存**: CI/CD環境など、どこでも確実にテストが通ります。
- **エッジケースの検証**: 「承認されている状態」「承認されていない状態」をダミー関数を変えるだけで簡単に作り出せます。

# おわりに

今回は `theme_observer` モジュールのリファクタリングを題材に、依存注入を用いてテスト容易性を劇的に向上させる手法を解説しました。

「ファイルパスや外部関数を引数に渡す」というシンプルな設計変更をするだけで、コードの見通しが良くなるだけでなく、堅牢で爆速なユニットテストを書けるようになります。

実務で「この関数、テストしようとしたら本番のファイルを触らないといけない...」と悩んだときは、ぜひ**「この外部への依存関係を、引数として外に追い出せないか？」**と考えてみてください。この小さな工夫が、システム全体の保守性と品質を大きく引き上げる鍵になります。
