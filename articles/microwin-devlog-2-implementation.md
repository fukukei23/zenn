## はじめに

前回の[【設計編】](https://zenn.dev/fukukei23/articles/microwin-devlog-1-design)では、「片付けガチャ」アプリ **MicroWin** の設計を複数の AI にレビューさせて、課金設計の自己矛盾や測定方式の穴を潰した話を書きました。

今回は**実装編**です。データ層（SQLite マイグレーション）を題材に、「AI との設計レビューで出た指摘を、コードの構造としてどう落とし込んだか」を記録します。

題材に選んだ理由はシンプルで、**個人開発でもスキーマは必ず変わる**からです。v1 でリリースした機能が v2 で変わる・列を追加する・型を直す — そのたびにユーザーの端末内データベースを壊さずに更新する仕組みがないと、アップデートでデータ消失します。趣味のアプリでも、ここを雑にすると後で泣きます（私は泣きたくないので作りました）。

## 前提: 何を作ったか

MicroWin のデータ層は React Native（Expo）+ **expo-sqlite** です。構成は次の2段階で作りました。

| 段階 | 内容 | テスト数 | カバレッジ |
|---|---|---|---|
| PR1 | マイグレーションフレームワーク+SQLiteアダプタ抽象化 | 98件 | 88.88% |
| Day 5+ | 本物の expo-sqlite SDK との統合 | 133件 | 90.57%（DB層は100%） |

TypeScript、テストは Jest、tsc と lint はゼロで維持しています。

## PR1: 設計レビューの指摘が「4つの構造判断」になった

まず、AI たちの設計レビュー（複数ベンダーの AI に同じ設計書を見せて独立にレビューさせるやり方）から出た指摘を、次の4つの構造判断として実装しました。

### 判断1: PRAGMA 操作をアダプタ層に閉じ込める

レビューで「マイグレーションランナーに PRAGMA 文字列を直接埋め込むな」と指摘されました。当初の案はランナー直埋めでしたが、指摘通りアダプタ層を作ると:

- テストでは Fake アダプタ（メモリ実装）で完結
- 本番では expo-sqlite 用アダプタに差し替え
- SDK を変えたくなっても **1 ファイルの修正で吸収**

「テストで Fake、本番で本物」を同じランナーのコードで回せるようになり、この後の Day 5+ がかなり楽になりました。

### 判断2: マイグレーション履歴はテーブルで管理する

`PRAGMA user_version` の数字だけだと「v1 は適用済みだが、テーブルが壊れている」という状態を検出できません。レビューで3体の AI が独立に履歴管理を指摘したため、`schema_migrations` テーブルを作り・適用済みマイグレーションを記録する方式にしました。

さらに「既存のデータベースが既に v1 相当だった場合に、誤って v1 を注入しない」という bootstrap 条件も、レビューで1体が指摘してテストを修正しています。

### 判断3: 1マイグレーション=1トランザクション

これも複数体が独立に指摘した critical です。DDL はトランザクションで包まないと、**途中で失敗したときに半分だけ適用された状態**が残ります。そうなるとリトライもロールバックもできず、端末ごとに壊れ方がバラバラになります。

「1 マイグレーション = 1 トランザクション = 失敗したら全部ロールバック」を契約として、ランナーに構造として埋めました。

### 判断4: 実装が終わったら、コード自体をもう一度レビューさせる

PR1 の設計レビューで 38 件の指摘が出て 11 件を採用した後、**実装コードを別のレビューにかけたら 36 件出て、そのうち critical 5 件を即日修正**しました。設計のレビューを通したからといって、実装の穴は消えません。この「設計レビュー → 実装 → 実装レビュー」の二段構えは、コストの割に効きました。

## Day 5+: 本物の SDK と繋いだら、2つ「想定と違う」ことが起きた

PR1 は Fake アダプタでの TDD だったので、本物の expo-sqlite（SDK 57）と繋ぐ段階で実機の制約に直面しました。

### 起きたこと1: React Native のランタイム（Hermes）に TextEncoder がない

チェックサム計算を Node の crypto で書いていた部分を、本番では expo-crypto に置き換える必要がありました。ここで選択肢が3つ:

1. **expo-crypto の digestStringAsync に切り替え**（文字列を直接受けられる）
2. crypto の digest（Uint8Array 受け）を維持し、文字列→Uint8Array 変換を自前実装
3. polyfill ライブラリを足す

2 は **Hermes に TextEncoder が存在しない**ため、UTF-8 エンコードを自前で書くことになります。エンコードを自前実装するのは監査リスクが高く、3 は依存が増えて Expo の推奨経路から外れます。結果、1 の「インターフェースを非同期化する」方式にしました。インターフェースの破壊的変更（ランナー 2 箇所+テストの期待値計算）は、修正範囲が小さくて済みました。

### 起きたこと2: トランザクションの「スコープ外巻き込み」

expo-sqlite の `withTransactionAsync` は、公式ドキュメントの実測ベースで**スコープ外のクエリもトランザクションに巻き込む**挙動がありました。async/await の性質上、避けられないものです。マイグレーション用途では「この範囲だけを確実にトランザクションに含めたい」ので、排他的スコープを提供する `withExclusiveTransactionAsync` を採用しています。

このあたりは「本物の SDK を読むまで分からない種類の問題」で、Fake のテストは全部緑でした。Fake での TDD と本物 SDK での統合テスト、両方の価値を思い出させられた局面です。

## 数字で見ると

- テスト: 98件（PR1）→ **133件**（Day 5+）・全て緑
- カバレッジ: 88.88% → 90.57%（SQLite アダプタとマイグレーション本体は **100%**）
- 設計レビュー 38 件 → 採用 11 件 / 実装レビュー 36 件 → critical 5 件を即修正
- 機械チェック（tsc・lint）は常にゼロを維持

## 学び: 指摘は「そのまま実装する」のではなく「構造選択として再考する」

今回いちばん効いたのは、**レビューの指摘をそのまま実装せず、選択肢を3つくらい並べて「なぜそれを採るか」を書いてから実装する**やり方でした。

指摘そのものは正しいことが多いですが、実装の形は複数あり得ます。checksum 非同期化の3案のように「指摘は同じでも、採る構造で将来の負債が変わる」場面が必ず来ます。選んだ理由を記録しておくと、後日「なぜこれで作ったんだっけ」と聞かれたとき（大体は未来の自分です）に答えられます。

なお、設計編で書いた通りこのプロセスでは「AI の指摘を採用したら、その修正に新たな穴が生まれていないか」を別ラウンドのレビューで確認しています。実装編のここで紹介した判断たちも、前回の記事と同じレビューの枠組みで複数体の AI に叩かれています。
