# はじめに

Claude Codeの設定一式（CLAUDE.md、hooks、SKILLなど）を単一のGitリポジトリで管理する「SSOT運用」をしています。複数マシン・複数セッションから同じ設定を参照させるため、ローカルの設定ディレクトリとリポジトリを常に同期し、**「何を・どこに・どの粒度で記録するか」をSKILL.mdにルール化**して運用しています。

そのルールの1つに「関連パターンを記録しますか？ [y/N]」という二者択一の確認質問があったのですが、これが原因でLLMの挙動がたびたび不安定になりました。本記事では、この質問を廃止して **N / H / R の3値ルールによる自動判定** へ置き換えた話を紹介します。地味な変更ですが「質問による停止」と「記録粒度の揺れ」が同時に解消された、実体験ベースの改善です。

# 1. [y/N]質問がLLMを惑わせていた実例

もとのSKILL.mdには、次のような指示がありました。

```markdown
- 関連パターンとして記録できる場合は、ユーザーに確認すること：
  「関連パターンとして記録しますか？ [y/N]」
```

一見すると丁寧な設計に見えますが、実際には3つの問題が起きていました。

**（1）「確認すべきケース」の境界が判断できない**
タイムアウト値の変更のような小さな修正でも質問が飛んできたり、逆に明らかに知見が残る場面で勝手に詳細な記録を作り始めたりと、LLMの判断が揺れました。「関連パターンに値するか」の基準が定義されていなかったためです。

**（2）質問が発生するとワークフローが止まる**
回答を待つ間、処理が完全に停止します。人の席にあるときはまだしも、夜間に回している自動タスクがここで止まるのは致命的でした。

**（3）二値では「記録の強度」を表現できない**
実務上のほとんどのケースは「履歴に1行残せば十分」な中間的なものでした。しかし質問は「パターン化する／しない」の二択しかないため、回答と実際の記録粒度が乖離しがちでした。

要因を一言でいうと、**人間向けUIである「確認質問」を、LLM向けのプロンプトに混入してしまった**ことです。

# 2. 3値ルール（N/H/R）への置き換え

対策として、質問そのものを廃止し、記録分類を3値に増やしてLLMに自動判定させます。

| 分類 | 意味 | 記録先 | 例 |
|---|---|---|---|
| **N** | 記録なし | なし | 誤操作のやり直し、単なる同期コミット |
| **H** | 履歴のみ | 履歴ファイルに1行 | 設定値の変更など「いつ何をやったか」が辿れれば十分な事実 |
| **R** | 関連パターン | パターンファイルに構造化 | 再発しうるトラブルと対処のセット |

SKILL.mdの記述はこう変わりました。

```markdown
- 記録分類は N / H / R の3値からLLMが自動判定する（ユーザー確認は不要）：
  - N: 再利用価値がない一過性の作業。履歴にも残さない
  - H: 事実の記録として価値があるが、再利用はしない。日時＋1行で履歴に追記
  - R: 同じ失敗・対処が再発する知識。原因・対処・条件を構造化して記録
- 判定に迷う場合は H をデフォルトとする
```

ポイントは2つです。

1. **デフォルトをHに固定**したこと。迷いを「質問」ではなく「中間値」で吸収します
2. **Rの条件を具体的に列挙**したこと（例：同じエラーへ対処を書くのが2回目、環境をまたいで再現する手順）。「質問しない」代わりに基準を与えるのが本質です

# 3. 変動可能性ルールとの組み合わせ

3値化と同時に、調査系の記録（リポジトリ内では30_RESEARCHと呼んでいる区分）向けに「変動可能性ルール」も追加しました。同じ知識でも「今後変わるか」で扱いが変わるためです。

- **変動が大きい**（暫定結論、ツールのバージョン依存の挙動）→ H寄り。パターン化すると古い情報が残り続ける危険がある
- **変動が小さい**（検証済みの原因→対処の因果）→ R候補

判定ロジックの骨格をPythonで書き下すと、こうなります。

```python
from dataclasses import dataclass
from enum import Enum

class RecordClass(Enum):
    N = "no_record"        # 記録なし
    H = "history_only"     # 履歴のみ（1行）
    R = "related_pattern"  # 関連パターン（構造化）

@dataclass(frozen=True)
class Decision:
    cls: RecordClass
    reason: str

def classify(is_reusable: bool, is_volatile: bool, has_fact: bool) -> Decision:
    """3値＋変動可能性から記録分類を決める骨格"""
    if not has_fact:
        return Decision(RecordClass.N, "記録に値する事実がない")
    if not is_reusable:
        return Decision(RecordClass.H, "再利用しない事実は履歴1行で十分")
    if is_volatile:
        return Decision(RecordClass.H, "変動可能性が高いため履歴に留める")
    return Decision(RecordClass.R, "安定した再利用知識はパターン化する")

# 動作イメージ
print(classify(is_reusable=True, is_volatile=True, has_fact=True))
# Decision(cls=<RecordClass.H>, reason='変動可能性が高いため履歴に留める')
```

実際の判定はPythonスクリプトではなく、SKILL.mdに書いた自然言語の基準をLLMが適用します。それでも**「コードとして書き下せる程度に曖昧さを潰しておく」**のが効果的でした。この疑似コードを書いてみたことで「再利用価値があるのに変動する情報」の扱いが抜けていることに気づき、変動可能性ルールの追加につながりました。

結果として、質問による停止はゼロになり、履歴ファイルは粒度が揃って検索しやすくなり、Rに分類される記録の精度も上がりました。

# おわりに

- LLMエージェント向けの運用ルールに**確認質問を安易に混ぜない**。質問は判断の揺れと停止を生む
- 選択肢を列挙し、**判定基準とデフォルト値を与えれば、LLMは安定して自己判断できる**
- 直感的には「選択肢は少ないほど簡単」に思えますが、**二値より三値のほうが判断が安定する**ケースがある。中間値が「迷ったときの避難所」になるためです

SSOT運用の地味な改善ですが、プロンプト設計の考え方としても応用できるはずです。同じような運用をしている方の参考になれば幸いです。
