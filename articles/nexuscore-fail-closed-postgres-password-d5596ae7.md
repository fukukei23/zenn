## はじめに

アプリケーション開発において、環境変数の管理は避けて通れない課題です。とくにデータベースのパスワードやAPIキーなどの機密情報は、環境変数経由で注入するのが一般的ですね。

今回は、私が開発に関わっている「NexusCore」というプロジェクトでセキュリティレビューを受ける機会があり、その際に指摘された **「fail-closed（フェイルクローズド）設計」** の重要性について学んだことを解説します。

「環境変数が設定されていなくても、とりあえずデフォルト値で動かす」といった実装をしていませんか？この記事では、環境変数未設定時にシステムを即座に停止させるfail-closed設計の考え方と、Pythonでの具体的な実装方法を紹介します。

## fail-open と fail-closed の違い

セキュリティ設計において、システムに異常やエラーが発生した際の振る舞いを定義する重要な概念があります。

### fail-open（フェイルオープン）
異常が発生した際、システムを**「開いた（通過する）状態」**にする設計です。
たとえば、環境変数が設定されていない場合、デフォルトのダミーパスワードを代入してアプリケーションを強制的に起動させるアプローチがこれに該当します。一見親切な設計に見えますが、本番環境で機密情報が漏洩した場合でもシステムが気づかずに動き続けてしまうため、重大なセキュリティインシデントに繋がる危険性があります。

### fail-closed（フェイルクローズド）
異常が発生した際、システムを**「閉じた（停止する）状態」**にする設計です。
必須の環境変数が設定されていない場合、アプリケーションはデフォルト値で誤魔化すことなく、**即座にエラーを吐いて起動を中止**します。

開発中はエラーで止まって鬱陶しく感じることもありますが、「安全が確保できないなら動かさない」という姿勢こそが、堅牢なシステムを構築するための第一歩なのです。

## POSTGRES_PASSWORD環境変数のfail-closed実装

それでは、NexusCoreプロジェクトのセキュリティレビューで実際に指摘された、「データベースのパスワード（`POSTGRES_PASSWORD`）」の扱いについて見ていきましょう。

### Before: fail-openな実装（危険な例）
以前のコードでは、環境変数が設定されていない場合に備えて、デフォルト値を設定してしまっていました。

```python
import os

def get_db_config():
    # NG例: 環境変数がなくてもデフォルト値で動いてしまう (fail-open)
    db_password = os.getenv("POSTGRES_PASSWORD", "default_password")
    
    # 本番環境で環境変数の設定ミスがあった場合、
    # "default_password" でDBに接続を試みてしまう...
    return db_password
```

この実装の恐ろしいところは、本番環境のデプロイ時に環境変数の設定を忘れてもアプリケーションがエラーを吐かずに動いてしまう点です。もし認証が緩いDBに接続されてしまうと、データが抜き取られる致命的な脆弱性に繋がります。

### After: fail-closedな実装（安全な例）
レビュー指摘を受けて、環境変数が未設定の場合は例外を発生させて処理を停止するように修正しました。

```python
import os
import sys

def get_db_config():
    # OK例: 環境変数が必須であることを明示する
    db_password = os.getenv("POSTGRES_PASSWORD")
    
    if not db_password:
        # fail-closed: 必須情報がない場合は即座にシステムを停止させる
        print("Error: POSTGRES_PASSWORD environment variable is not set.", file=sys.stderr)
        raise RuntimeError("Missing required environment variable: POSTGRES_PASSWORD")
    
    return db_password
```

このようにすることで、デプロイ時の設定ミスがあればアプリケーションの起動時に即座にエラーで気づくことができます。「フェイルファスト（Fail-Fast：早く失敗する）」の思想にも通じる、安全なアプローチです。

## NexusCoreプロジェクトにおけるセキュリティ向上の歩み

今回の`POSTGRES_PASSWORD`のfail-closed化は、NexusCore全体のセキュリティ強化の一環です。並行して行われたセキュリティレビューでは、他にも以下のような改善を実施しました。

- **シークレットスキャンの導入 (gitleaks)**: CI/CDパイプラインにシークレットスキャンツールを導入し、誤ってソースコードにパスワード等がコミットされるのを自動的に防ぐようにしました。
- **パスインジェクション対策**: APIのエンドポイントにおいて、意図しないディレクトリへのアクセス（IDOR: Insecure Direct Object Reference）を防ぐための入力値バリデーションを強化しました。
- **バックアップ戦略の整備**: SaaS本番環境向けのDBバックアップ戦略を整備し、サイドカー構成での日次バックアップや、暗号化・リストア手順を明確化しました。

セキュリティは単一の機能で完成するものではなく、環境変数の管理、CI/CDでの検知、APIの堅牢化など、多層防御の考え方でプロダクト全体を底上げしていく必要があります。

## おわりに

今回は、セキュリティレビューでの指摘を契機に学んだ「fail-closed設計」の真髄について、Pythonでの実装例を交えて解説しました。

「ないならないで動かす（fail-open）」アプローチは、一時的な開発の利便性をもたらすかもしれませんが、本番環境での致命的な事故の引き金になります。必須の設定が欠けているなら、勇気を持ってシステムを止める（fail-closed）。このシンプルな原則を徹底するだけで、システムの堅牢性は劇的に向上します。
