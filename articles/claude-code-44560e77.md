## はじめに

Claude Codeと開発を進めていると、一番怖い失敗は「コードが動かない」ことではありません。**「できる」と言ったことが、できないまま放置される**ことです。

私は自身のClaude Code運用設定を自分のリポジトリでバージョン管理しており、AIとの対話で起きた失敗を番号付きで記録しています。先日追加されたのが失敗⑫――**突破不能確定案件での「将来可能性の残響」による空約束誘発**です。

本記事では、①突破不能案件の見分け方、②対外返信スキルに追加した約束突合欄、③送信前の確認ゲート実装、の3点を紹介します。

## 1. 「できます」が刺さる瞬間：失敗⑫の構造

起きたことは単純です。機能提案のやり取りの中で、現時点では実現不可能な案件について、AIがこう返してしまいました。

> 現在の構成では難しいですが、将来的には対応できると思います。

一見誠実な返答に見えます。しかし相手に残るのは「対応できる」という部分だけ。数日後「例の機能、どうなりました？」と聞かれ、初めて約束していたことに気づく――これが空約束誘発です。

原因は2つあります。

- **LLMは依頼を肯定しがち**： 断る文よりも受ける文を生成しやすい
- **「将来はできる」と「今できる」の区別が文面に残らない**： 前置きの修飾節は読み飛ばされる

そこで私は、機能提案を受ける前に3つの質問を通すことにしました。**1つでもNoがあれば「突破不能確定案件」として扱い、回答文から肯定表現を排除します。**

1. 依存するAPI・機能は実在するか
2. 自分側の権限・スコープで操作できるか
3. 今すぐ再現・検証する手段があるか

## 2. 約束突合欄： 言ったことと見通しを機械的に突き合わせる

見分け方だけでは人間側の注意力頼みです。そこで対外返信（outward-reply）用の精読シートを7欄に拡張し、**約束突合欄**を追加しました。

運用の流れは次のとおりです。

1. **Phase 0で自側約束を抽出**： 対話全文を走査し、AI側が発した「〜します」「〜できます」をすべてリストアップ
2. **送信前に突合**： ドラフト内の約束と、実装見通し・突破不能判定を1行ずつ照合
3. **不一致は差し戻し**： 突破不能確定案件なのに肯定表現が残っていれば、書き換えるまで送信しない

あわせて「中途半端報告禁止（最小5禁止）」に、**機能提案の成功条件を明示する**ルールを追加しました。機能を提案するときは

- 何ができるようになるか
- 何はできないか（今回の境界線）
- できないものを実現する条件は何か

をセットで書く、というものです。「将来的にはできる」を言いたければ、その条件を具体的に書く義務があります。

## 3. 確認ゲートの実装例（Python）

最後に、この突合を送信前のフックとして自動化する簡易実装です。実運用では対話ログと連動させますが、エッセンスは以下の30行に凝縮されています。

```python
import re

# 自側発言に含まれがちな「約束」表現（ラベル付き）
PROMISE_PATTERNS = {
    "〜できます系": r"できます",
    "〜します系": r"(実装|対応|追加|修正|用意)します",
    "期限残響系": r"(近日中|次回|改めて|いずれ)",
}

def is_definitely_blocked(feasibility: dict[str, bool]) -> bool:
    """3条件チェック: 1つでも False なら突破不能確定案件"""
    return not all(feasibility.values())

def gate_reply(draft: str, feasibility: dict[str, bool]) -> str | None:
    """送信前ゲート: 突破不能案件への約束表現を検出したら差し戻す"""
    if not is_definitely_blocked(feasibility):
        return None  # 見通しが立っている → そのまま送信
    hits = [label for label, pat in PROMISE_PATTERNS.items() if re.search(pat, draft)]
    if not hits:
        return None  # 約束表現なし → そのまま送信
    return (
        "【ゲート差し戻し】突破不能確定案件への約束表現: "
        + " / ".join(hits)
        + " → 『現時点では不可、実現条件は◯◯』形式へ書き換えること"
    )

# --- 動作例 ---
feasibility = {
    "依存APIが実在": False,  # 対応するAPIが存在しない
    "権限で操作可能": True,
    "今すぐ検証可能": True,
}

draft = "承知しました。近日中に対応します！"
print(gate_reply(draft, feasibility))
# 【ゲート差し戻し】突破不能確定案件への約束表現: 〜します系 / 期限残響系 → ...
```

ポイントは**判定と文言を分離**していることです。突破不能かどうかは人間が3条件で判定し、ゲートは「その事実と矛盾する文面がないか」だけを機械的に見ます。責務が小さいので誤検知が減り、運用が長続きします。なお、同じリポジトリでは確認ゲートを一時的に省略するモード切り替えも試していますが、省略する場合も結果表示後に都合の悪い点を必ず修正するルールを併記し、抜け道を塞いでいます。

## おわりに

「できます」を安易に言わせない工夫は、AIを信用しない運用ではありません。**失敗を番号付きで記録し、スキルとコードに変換するサイクル**を回すことで、同じ穴に落ちる回数を減らしていく営みです。

今回の失敗⑫も、コミットとして記録 → 精読シートに約束突合欄を追加 → ゲートで自動差し戻し、という流れで仕組み化しました。皆さんの運用でも「言ったこと」と「やれること」の突合を自動化してみてください。最初の一歩は、対話ログから自分の約束を抜き出す10行のスクリプトで十分です。
