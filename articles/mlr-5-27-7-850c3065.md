## はじめに

LLMにコードレビューを頼むとき、誰もが一度は悩むことがあります。「この指摘、本当に直すべき？」という問題です。1機のレビューなら見逃しや幻覚がありますし、かといって複数のLLMにレビューさせるMulti-LLM Review（MLR）を試すと、指摘が洪水のように押し寄せます。

私が自分のClaude Code設定リポジトリ（claude-config）のhookスクリプトに対して5機のLLMレビューを実施したところ、初回ラウンドで4項目の採用修正を行い、続く追加レビュー（r1）では**27件もの指摘**を受けました。27件全部を直せばdiffは膨らみ、修正自体のリスクが無視できなくなります。直さなければレビューした意味がありません。

本記事では、その27件を**7項目に絞り込んだ判断軸**を、実測値とともに紹介します。

## セクション1：MLRの仕組みと27件の内訳

MLRの仕組みはシンプルです。設定リポジトリの `self-inspect` というサブコマンドが、同じレビュープロンプトを複数のLLMに投入し、指摘を重複除去して1つのリストにまとめます。

出てきた27件を分類すると、おおよそ次のような構成でした。

- 実害のある潜在的欠陥（誤検知、リソースリーク）
- 特定条件でのみ壊れる頑健性の問題（cron環境のPATH、文字コード）
- 仕様変更の提案や命名への意見
- 再現手順のない「こうすべきでは」レベルの主張

つまり**機数を増やすほど指摘は増えるが、ノイズの割合は変わらない**のです。ボトルネックはレビューそのものではなく、指摘のトリアージ（仕分け）でした。

## セクション2：27件を7項目に絞る4つの判断軸

全指摘を次の4軸でスコア化しました。

**軸1：priority ― ただし「実測」がセットでないと点数にしない**

LLMはhigh/medium/lowとラベルを付けますが、それはレビュアーの主観にすぎません。私は「通知が連打される可能性」という指摘に対し、実際に「1時間で14回送信された」という実測が取れたものだけ最優先扱いにしました。

**軸2：影響範囲（global / local）**

hooksとcronで共有する共通基盤への指摘はglobal、単一スクリプト内の問題はlocal。1回の修正で全体が改善されるglobal指摘を高く評価します。

**軸3：テスト可否**

修正後に「直ったことを証明するテスト」を書けるか。書けない指摘はどれだけ深刻そうに聞こえても見送りです。

**軸4：他hookとの相互作用**

修正が他hookの挙動を変えるものは爆発半径が広いため、同じラウンドでは採用しません。実際に「hook同士の二重touch競合」の指摘がありましたが、影響がバルーン通知の重複だけだったため、コメントに文書化して将来のlockfile再設計まで見送りました。

トリアージのコードはこうなります。

```python
from dataclasses import dataclass

@dataclass
class Finding:
    priority: str      # LLMのラベル（"high"など）
    scope: str         # "global"（共通基盤）/ "local"（単一スクリプト）
    testable: bool     # 回帰テストを書けるか
    interacts: bool    # 他hookの挙動を変えるか
    observed: bool     # 実測（実際に起きた証拠）があるか

def triage(findings: list[Finding]) -> tuple[list[Finding], list[Finding]]:
    """4軸でスコア化し、採用/見送りを仕分ける"""
    adopt, defer = [], []
    for f in findings:
        score = 0
        # 軸1: priority単独では加点しない。実測とのセットで加点
        score += 2 if (f.priority == "high" and f.observed) else 0
        # 軸2: 影響範囲が広い共通基盤への指摘
        score += 2 if f.scope == "global" else 0
        # 軸3: テストで回帰を証明できる
        score += 1 if f.testable else 0
        # 軸4: 他hookに波及するものは別ラウンドで慎重に
        score -= 2 if f.interacts else 0

        (adopt if score >= 3 else defer).append(f)
    return adopt, defer
```

ポイントは、priority単独では1点も入らないことと、相互作用が**減点**要素であることです。単純な重み付けではなく「直すことで壊しうるもの」を排除する設計です。

## セクション3：採用7項目の実態と次ラウンドでの気づき

採用した7項目の代表例です。

- **カバレッジ測定の信頼性**：Stmts（測定対象文数）が0でも100%と表示される偽装を防ぐ検証と `--cov-fail-under` の追加
- **30サンプル昇格判定**：主観的な「使えそう」ではなく、30サンプルの実績を集めてから正式採用を判断するルール
- **生出力貼付の必須化**：検証コマンドの生出力を報告書に貼らないと完了とみなさない。LLMが「緑でした」とそれっぽく書くのを防ぐ
- **必須項目の強く推奨への格下げ**：Phase 0の実運用と合っていなかったドキュメント側の修正

そして次ラウンド（r2）では追加で6項目を採用したのですが、ここでの気づきが大きかったです。口語化していた判断基準を**定量閾値に置き換えた**のです。例えば「テスト≥28/30が緑」「ラウンド数≤2」「assert密度≥0.5」。人間の最終確認（human-in-the-loop）は残しつつ、基準が数値になったことで**誰が判断しても同じ結論になる**ようになりました。

## おわりに

5機MLRから得られた教訓をまとめます。

1. 機数を増やすと指摘は増えるが、真のボトルネックはトリアージである
2. priority（実測必須）/ 影響範囲 / テスト可否 / 他hookとの相互作用の4軸があれば「なぜこれは採用しないのか」も説明できる
3. 27件全部を直すより、7項目に絞って実測とテスト付きで直すほうが品質は上がる
4. 判断基準は数ラウンド運用した後で数値化すると再現性が高まる

LLMによるレビューは安価になりましたが、「何を採用するか」の判断はまだ人間の仕事です。その判断のための枠組みを言語化しておくことは、自動化を進める上での土台になると感じています。
