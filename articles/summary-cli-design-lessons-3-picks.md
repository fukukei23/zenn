# はじめに

日々の開発を自動化するCLIツールやシェルスクリプトは、「動き出した後」にこそ罠が潜みます。この記事は、私が実際に運用していて踏んだ3つの失敗——**正常なコマンドが止まる・終了コードが衝突する・レア欠陥が残り続ける**——を、それぞれの原因と対策と一緒にまとめたものです。

どれも「一見正しそうなコード」が原因でした。「自分は大丈夫」と思っている人にこそ、読んでほしい内容です。

# 1. 正規表現の貪欲マッチで、ガードが無実のコマンドを止めた

危険コマンド（`rm -rf` 等）を自動ブロックするフックを運用していたとき、`git push origin main` という無害なコマンドまで止められる事故が起きました。

原因は、コマンド部分を抽出していたこの1行です。

```python
m = re.search(r'"command"\s*:\s*"(.*)"', stdin_text)
```

`.*` は**可能な限り長くマッチしようとする貪欲マッチ**です。入力が1行JSONのとき、`"command": "..."` の閉じクォートではなく、行末に近い別のクォートまで飲み込んでしまい、description に書いた「rm 系コマンドは使わない」という文章まで「コマンド」として検査されていました。

**対策の要点**は3つです。

- 貪欲 `.*` ではなく、クォートを含まない制約付きの `([^"]*)` を使う
- JSONのパースは正規表現ではなく `json.loads` に任せる
- 「誤ブロック」を検知するテスト（無実のコマンドが通ること）を先に書く

教訓はシンプルで、**「とりあえず正規表現でJSONを切る」は、データの形が1つでも変わった瞬間に壊れる**ということです。

# 2. exit code 5 は「自分だけの番号」ではなかった

記事の変換結果であるHTMLのcommit漏れで公開ページが404になる事故を受け、Git管理下に無い生成物を検知して異常終了するCLIを書いたときの話です。最初は終了コードに `5` を選びましたが、これが **pytest の予約済みコード（テストが1件も収集されなかった）と完全一致**していました。

終了コードには暗黙のしきたりがあります。

| 番号 | 意味 |
|---|---|
| 0 | 成功 |
| 1 | 一般的な失敗 |
| 2 | CLIの使い方誤り |
| 120〜128, 130, 137 | シェル・シグナル関連 |
| 5 | pytest: 収集ゼロ |

**対策**として、衝突しにくい **78** という番号に変更し、「なぜ78なのか」をREADMEと `--help` に明記しました。終了コードを選ぶときは、次の3点を確認するのが安全です。

1. 使うツール群の予約済み番号を調べる（pytest やシェルの特殊コード）
2. 自分の番号を文書化する（暗記頼みにしない）
3. パイプライン全体で exit code の一覧を1箇所に集約する

# 3. 毎日動くスクリプトには「レア欠陥」が積もる

毎日ObsidianのSSOTをGitHub Pagesへ同期するシェルスクリプトを運用していますが、「動いているからOK」と放置していた頃、ローカルファイルが意図せず消えかける事故が起きました。そこで複数のLLMに同じスクリプトをレビューさせ、指摘の重なり方で優先度を決める方法を試したところ、**5件の欠陥**が見つかりました。

多かったパターンは次の2つです。

- **エラーを握りつぶす `|| true`**: 失敗が成功として記録され、後で原因を追えなくなる
- **一時ファイルの後始末漏れ**: trap で確実に消す設計にしていなかったため、失敗時にゴミが残る

重要なのは、LLMの指摘は「候補」であって「結論」ではないこと。誤検知は人間が捨てる前提で、**複数モデルの一致だけをCritical扱いにする**と、一人レビューでは拾えない欠陥に気付けます。

# おわりに —— 3つの失敗に共通するもの

今回まとめた3つの失敗は、すべて「**その場では動くが、想定外の入力・隣のツール・時間経過**で壊れる」タイプでした。

- 貪欲マッチ → 入力の「形」が変わったとき壊れる
- exit code衝突 → 隣のツールと組み合わさったとき壊れる
- レア欠陥 → 時間が経ったとき壊れる

CLIは一度作ると黙って働き続けるぶん、壊れたときの被害も静かに蓄積します。「動いた」で終わらせず、入力の揺らぎ・周辺ツール・運用期間の3点を一度見直してみてください。
