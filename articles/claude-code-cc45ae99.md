## はじめに

Claude Codeに記事の生成から公開までを任せる運用をしていると、速度は上がる一方で「公開したら図が消えていた」「テーマを切り替えたら図の中の文字が見えなくなっていた」といった問題に度々悩まされました。

この記事では、その解決のためにパイプラインを「**原稿**」「**図解**」「**検査**」の3つに分離し、小さな自動テストで支えるようにした経緯を紹介します。私の環境はGitHub Pagesでドキュメントを公開するリポジトリですが、考え方は「CIでMarkdown記事を検証したい」人全般に応用できるはずです。

## 原稿・図解・検査を分離する

最初は「Claude Codeに全部任せる」方向で試していました。原稿を書かせ、図も描かせ、そのまま公開する。しかしこの方式では次の問題が出ます。

- 文言修正と図の修正が混ざり、何が変わったかレビューしづらい
- 図のSVGが壊れていても気づかず公開される

そこでClaude Codeへの指示書（SKILL.md）を役割ごとに分けました。ポイントは、**原稿側には `::: diagram 066-4` のようなディレクティブだけを書かせる**ことです。図の中身をMarkdownに埋め込ませず、独立したSVGファイルとして管理します。

変換スクリプトはディレクティブを見つけたら対応するSVGを探し、存在しなければ代替テキスト入りのプレースホルダを差し込んで警告を出します。ここはビルドを止めず警告に留める（fail-warn）設計にして、「図がまだ無い原稿」も執筆をブロックしないようにしました。

## CSS変数でテーマに追従させ、保証する色は固定する

図解を組み込んだ当初、ライトテーマでは見た目が整っても、ダークテーマに切り替えると図の中の文字が背景に溶けていました。SVG内で色を固定していたためです。

解決策は、文字色を `var(--text)` のような**CSS変数**に置き換え、図解用の `.story-diagram` クラスでダークテーマ用の4色を定義することでした。これでテーマ切り替えに図が自動で追従します。

ただし全部を変数化すると、今度はコントラスト検査に落ちる箇所が出ました。数字バッジなど一部の要素は色を `#4f46e5` に固定し、**両テーマでコントラスト基準を満たす**ようにしています。「テーマに任せる箇所」と「固定して保証する箇所」を切り分けるのがコツです。

## fail-closedなSVG許可リスト検査

MarkdownにSVGを埋め込めるようにすると、壊れたSVGや悪意のあるSVGが混入するリスクが生じます。SVGはXMLなので `<script>` を含められたり、`<!ENTITY>` 経由の攻撃（XXE）など、HTMLに似た危険を持ち込みます。

そこで「**許可リストにないものは全て拒否**」するfail-closed方式の検査をPythonで実装しました。原稿段階と公開物段階の二層で同じ検査をかけています（二層防御）。

```python
import re

ALLOWED_TAGS = {
    "svg", "title", "desc", "defs", "g", "path", "circle",
    "rect", "text", "tspan", "linearGradient", "stop",
}

def inspect_svg(svg_text: str) -> list[str]:
    problems = []
    # 1) エンティティ定義は全面拒否（XXE対策）
    if re.search(r"<!ENTITY", svg_text, re.I):
        problems.append("<!ENTITY> is not allowed")
    # 2) style属性は拒否（CSSの注入経路を塞ぐ）
    if re.search(r"\sstyle\s*=", svg_text, re.I):
        problems.append("style attribute is not allowed")
    # 3) SMILアニメーションは拒否
    if re.search(r"<(?:animate|set|animateTransform|animateMotion)\b", svg_text):
        problems.append("SMIL animation is not allowed")
    # 4) タグを列挙し、許可リスト外はすべて拒否
    for tag in set(re.findall(r"<([a-zA-Z][\w:.-]*)", svg_text)):
        if tag not in ALLOWED_TAGS:
            problems.append(f"tag not in allowlist: {tag}")
    return problems
```

設計上のポイントは3つです。

- ブラックリスト（`script` だけ禁止など）ではなくホワイトリストなので、**未知の危険なタグも自動的に落ちる**
- `url(#gradient-1)` のようなSVG内部参照だけは例外的に許可（グラデーション参照に必要なため）
- 図のキャプション（figcaption）はSVG内の `desc` 要素を流用し、無ければslugからフォールバック生成

この検査込みでテストは十数件程度。小さく保っているので、記事を1本追加するたびに全部回しても数秒で終わります。テストはディレクティブ検知からSVG検査まで、実装前に先に書くTDDで進めました。

## assetsコピー問題：生成物を直接編集しない

最後に一番地味で一番効いた教訓です。図解のCSSを調整するため公開物側（docs配下）を直接編集したところ、次の変換実行で**すべて元に戻ってしまいました**。調べると、変換スクリプトが `assets/` から `docs/assets/` へ毎回上書きコピーする構造になっていたのです。

対策は単純で、CSSをコピー元の `assets/` 側に適用することでした。つまり「**生成物ではなくソースを編集する**」。パイプラインが正しく同期しているかは、生成HTMLを正規化してハッシュ比較する仕組みで検証し、差分0件を確認して完了としました。

## おわりに

まとめると次の4点です。

- 生成（原稿・図解）と検査を分離し、`::: diagram` ディレクティブで結合する
- SVGはfail-closedな許可リストで二層防御する
- テーマ依存の色はCSS変数、保証したい色は固定と切り分ける
- 生成物は直接編集せず、コピー元を更新する

この構成にしてから「公開後に図が崩れていた」が起きなくなりました。エージェントに公開パイプラインを任せるなら、人間の目が届かない分、小さな自動検査で足場を固めるのが有効だと感じています。
