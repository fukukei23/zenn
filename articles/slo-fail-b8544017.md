## はじめに

公務員からIT業界に転職し、いまはとあるOSSプロジェクトのベンチマークリポジトリで性能測定とその「合否判定」の運用を担当しています。

ベンチマークを回すだけであれば、時間を計って結果を記録すれば終わりです。しかし運用として大事なのはその後で、「**この変更は今までより悪くなっていないか？ 悪くなっていたら元に戻すべきか？**」を機械的に、誰が見ても同じ結論になるように判定することです。この記事では、そのために導入した3つの仕組みを初心者向けに解説します。

1. **INSUFFICIENT_DATA判定**（データ不足で誤ロールバックしない設計）
2. **fail条件の50runスライス化**（直近データだけを見る判定）
3. **ロールバック閾値の設計思想**（数字は実測から決める）

## 「まだ分からない」は「悪い」ではない —— INSUFFICIENT_DATAという第三の状態

SLO（Service Level Objective）とは、サービス品質の目標値のことです。「タイムアウト率〇%以下」といった形式で決めます。そしてSLOゲートとは、新しい変更（カナリア）を投入した後、SLOを満たしているかを判定し、満たさなければ自動でロールバックする仕組みです。

ここで初心者が陥りがちなのが、判定を「合格 / 不合格」の**2値**で作ってしまうことです。

実際に私が運用で経験した場面を挙げます。ある日、タイムアウトを600秒に変更したカナリアのSLO判定を実行したところ、判定対象のrunは**0件（必要30件に対して0/30）**でした。もし2値判定であれば、この時点で「FAIL → ロールバック」が発動してしまいます。

しかしデータが**ないだけ**です。悪くなった証拠は何もありません。ここでロールバックしてしまえば、変更はデータ不足だけで却下され、原因の分析もできません。

そこで判定に第三の状態 **INSUFFICIENT_DATA** を導入しました。AWSのCloudWatchアラームにも同名の状態があり、「OK」「アラーム」に並んで「データ不足」が用意されているのと同じ発想です。前職の公務員時代に身についた「判断できないものは、判断できないと記録する」という文化が、そのまま生きた瞬間でした。

## fail条件の50runスライス化と、ロールバック閾値の設計思想

次の問題は「どの範囲のデータで判定するか」です。全期間のデータで判定すると、古い測定条件の結果が混ざり、いまのシステムの状態を見誤ります。そこでfail条件は**直近50runだけをスライス**して判定するようにしました。窓が満たないうちは前節のとおり蓄積待ち（INSUFFICIENT_DATA）です。

また、ロールバック閾値は「エラー率◯%」のような数字にしたくなりますが、**この数字は憶測ではなく実測から決める**のが鉄則です。私のケースでは、57run分の実データを解析してタイムアウトの連鎖パターンを調べ、さらにn=12の検証計測（タイムアウト0/12・最長579秒）を経て、ようやく600秒というタイムアウト値と合格基準を根拠付きで決定しました。

判定スクリプトの簡略版がこちらです。ポイントは**処理の順序**で、(1)フィルタ → (2)蓄積待ち判定 → (3)fail判定の順に置いていることです。

```python
from dataclasses import dataclass

FAIL_SLICE_SIZE = 50   # fail判定に使う直近run数
MIN_RUNS = 30          # この数に満たない場合は蓄積待ち

@dataclass
class GateResult:
    status: str    # "OK" | "FAIL" | "INSUFFICIENT_DATA"
    runs_used: int
    detail: str

def judge_gate(runs, expected_timeout_sec=600, slo_error_rate=0.05):
    # (1) 誤投入防止フィルタ: 測定条件が異なるデータを機械的に除外
    valid = [
        r for r in runs
        if r["timeout_sec"] == expected_timeout_sec
        and r["measured_at"] is not None  # 記録時刻が正しく残っているrunのみ
    ]

    # (2) 最初に蓄積待ち判定 —— データ不足では絶対にFAILを出さない
    if len(valid) < MIN_RUNS:
        return GateResult(
            "INSUFFICIENT_DATA", len(valid),
            f"蓄積待ち（{len(valid)}/{MIN_RUNS}）: ロールバック条件に非該当",
        )

    # (3) 直近50runだけをスライスしてfail条件を判定
    recent = valid[-FAIL_SLICE_SIZE:]
    errors = sum(1 for r in recent if r["timed_out"] or r["exit_code"] != 0)
    error_rate = errors / len(recent)

    status = "FAIL" if error_rate > slo_error_rate else "OK"
    return GateResult(status, len(recent), f"error_rate={error_rate:.3f}")
```

この順序を守るだけで「データ不足による誤ロールバック」と「条件違いデータによる汚染」を構造的に防げます。

## 誤判定を防ぐのは機械的なフィルタとテストの積み重ね

設計が正しくても、運用では思いがけない事故が起きます。私も実際、**過去の測定条件のデータが混入してROLLBACKと誤判定された**ことがありました。原因は、判定スクリプトに古いデータが入ってしまったこと。人手の確認で防ごうとするのではなく、`timeout_sec` と記録時刻（ts）を**機械判定するフィルタ**をスクリプトに追加して解消しました。

さらに、判定ロジック自体のテストも拡充しました。単純なOK/FAIL経路だけでなく、exit 0で正常終了する経路、閾値の秒境界、非UTCのタイムゾーンオフセット、引数なし実行、シード値の除去漏れなど、地味なケースを含めて最終的に28テストすべて緑になるまで固めました。自己点検の過程で、**ドキュメントに書いた数値がコードの挙動とズレていた（数値ドリフト）**ことも発見できています。判定器こそ、一番テストが必要なコードです。

## おわりに

初心者向けに、ベンチマークのSLO運用で大事だと学んだ3つの原則をまとめます。

- **不明は不明と記録する**：INSUFFICIENT_DATAという第三の状態により、データ不足での誤ロールバックを防ぐ
- **直近だけを公平に見る**：fail条件を50runスライス化し、常に「いまの」状態を評価する
- **数字は実測から決める**：ロールバック閾値は解析と検証計測に裏付けられた根拠付きで設定する

SLOというと大規模サービスの話に感じますが、本質は「判定の設計」であり、個人のベンチマークスクリプトでも今日から実践できます。この記事が同じく転職して運用を任された方の助けになれば嬉しいです。
