## はじめに

個人開発でも長く続くプロジェクトになると、小さな問題が少しずつ溜まっていきます。「後で直そう」と思ったまま、何がどこに溜まっていたか忘れてしまう――そんな経験はありませんか。

私が管理しているリポジトリ（atelier-kyo-manager）では、定期的に「包括的リポジトリレビュー」を行い、見つけた指摘を **issue-backlog形式のMarkdownドキュメント** に記録する運用をしています。直近のレビューでは14件の指摘を記録し、うち1件だけをその場のPRで修正、残り13件はバックログとして残しました。

この記事では、その進め方をテンプレート付きで紹介します。ポイントは次の3つです。

1. **推測ゼロ**：指摘はすべて実環境で再現確認したものだけを残す
2. **記録の資産化**：リポジトリ内ドキュメントに構造化して保存する
3. **段階的修正**：1つのPRで直すのは高優先度1件、残りは優先度順のバックログへ

## 推測ゼロ実測レビュー — 「走らせて確認した指摘だけを残す」

コードレビューで一番よくないのは、「たぶんバグってる」といった推測の指摘を溜め込むことです。誤報が混ざると指摘リスト全体の信頼が下がり、後で拾う気も失せてしまいます。

そこで今回のレビューでは、P0（最優先）／P1（高優先）に分類した指摘は **すべて実際にコードを走らせて再現を確認** することをルールにしました。

- Python 3.11 + venvを新規構築し、依存関係をクリーンな状態からインストール
- テストスイートを通しで実行し、失敗の有無とカバレッジを確認
- 疑わしい挙動は最小のスクリプトを書いて再現

実際に確認できた指摘の例です。

- `.gitignore` の途中の行が壊れており、意図した除外が機能していない（`git status` で意図しないファイルが出現することを実確認）
- gif生成の中間出力900件や大量のカタログ画像がリポジトリに追跡されていた（実容量を測定して確認）
- 16ファイルが実行ビット付きで追跡されていた（`git ls-files -s` でファイルモードを確認）

どれも「コードを見て怪しい」ではなく「コマンドを実行して観測した」事実だけを記録しているのがポイントです。

## issue-backlog形式で14件を記録する

記録は `docs/REVIEW_ISSUES_<日付>.md` のようなファイル名でリポジトリにコミットします。GitHub Issueではなく、あえてリポジトリ内ドキュメントにする理由は **コードと同じPR・同じ履歴でレビューできる** からです。

各エントリのテンプレートがこちらです。

```markdown
## ISSUE-XXX: 一行サマリ
- 優先度: P0 / P1 / P2
- 状態: 未対応 / 修正済み(PR #NNN) / 見送り
- 再現手順:
  1. 実行したコマンドや操作
- 確認結果: 実測で観測した挙動
- 影響範囲: 影響する機能・ファイル
- 対応方針: 直すならどう直すか
```

実例を簡略化すると、こんな形のエントリになります。

```markdown
## ISSUE-114: overrides_storeのバックアップ先がCWD依存
- 優先度: P1 / 状態: 修正済み(本PR)
- 再現手順: リポジトリ外のディレクトリからCLIを実行してバックアップを作る
- 確認結果: バックアップが実行時のカレントディレクトリ直下に生成された
- 影響: 実行場所によって保存先が変わり、ファイルが散らばる
- 対応方針: 設定のベースディレクトリを起点にパスを解決する
```

「確認結果」に実測内容を必ず書くのが、推測ゼロ運用の肝です。半年後に自分が読み返しても「これは再現済みの事実だ」と信用して着手できます。

## 1件だけ直して13件は残す — 段階的修正の進め方

14件見つかったからといって、1つのPRで全部直すのは避けるべきです。変更が巨大になるとレビューできず、副作用のリスクも増します。今回のPRは次のコミット構成にしました。

| コミット | 内容 |
|---|---|
| docs | レビュー結果14件の記録を追加 |
| fix | `.gitignore` の壊れた行を修正 |
| fix | overrides_storeのCWD依存を解消（ISSUE-114） |

docs（記録）とfix（挙動変更）を別コミットにするのは、履歴を見たときに「何が記録で何が変更か」を明確に分けるためです。

修正したISSUE-114は、いわゆる **CWD（カレントワーキングディレクトリ）依存** の問題でした。CWDとは「コマンドを実行したときの自分の居場所」です。相対パスはCWDを基準に解決されるため、実行場所が違えば同じコードでも違う場所を指してしまいます。

```python
from pathlib import Path

# 修正前: 相対パスのためCWD依存。
# どこから実行したかで保存先が変わってしまっていた
def backup_path(filename: str) -> Path:
    return Path("backups") / filename

# 修正後: 設定から解決したベースディレクトリを明示的に受け取る
def backup_path(base_dir: Path, filename: str) -> Path:
    return base_dir / "backups" / filename
```

修正後は、リポジトリ内とリポジトリ外の両方のディレクトリから実行して、保存先が変わらないことを確認してからコミットしました。修正を「記録どおりに再現が収まったか」の実測で締めるわけです。

またこのリポジトリでは、別途「変更履歴」ドキュメントを運用し、修正ごとにエントリを追加しています。二重管理のコストはありますが、「何をいつ直したか」を追えるのは長期プロジェクトで効いてきます。

## おわりに

この記事で紹介した運用をまとめます。

- レビュー指摘は実環境で再現確認してから記録する（推測を混ぜない）
- 記録はリポジトリ内のissue-backlog形式ドキュメントに残し、PRでレビュー可能にする
- 修正は「1 PR 1件」から始め、残りは優先度順のバックログとして扱う

「全部今すぐ直す」でも「全部後回し」でもなく、**全部記録して少しずつ直す**。長く続ける個人開発のリファクタリングを、地に足のついた形で進めるための参考になれば幸いです。
