# はじめに

AI駆動開発を始めて数ヶ月、あるアンチパターンに悩まされました。AIに設計やドキュメント作成を頼むと、**「一般的に推奨されています」「ベストプラクティスとしては」**といった出典のあいまいな推奨文が生成されることがあります。これを確認せずにPRや設計書へ転記すると、自分のプロジェクトの文脈と合わない推奨が「それっぽい文章」として量産されてしまいます。

厄介なのは、この手の文章がもっともらしくて人間のレビューでは見逃しがちなことです。そこで筆者は、Claude Codeの**Stop hook**を使って「テンプレート由来の推奨を無批判転記していないか」を機械的に検出する仕組みを作りました。本記事ではその設計と実装、運用で学んだことを紹介します。

# どんなアンチパターンを検出したいのか

具体例で説明します。設定ファイルのテンプレートをAIに読み込ませて設計を提案させると、次のような文が返ってくることがありました。

> テンプレートではerrorレベルが推奨されているため、そのまま採用します。

一見正しそうですが、よく見ると問題だらけです。

- そのプロジェクトが「学習中のチームなのでまずはwarning運用にする」と決めていた文脈が無視されている
- 「推奨」の出典（テンプレのどこに書いてあるのか）が不明
- 検討した形跡がなく、転記だけが成果物に残る

ポイントは、「テンプレートに推奨と書いてある」こと自体が悪いのではなく、**自分のプロジェクトの文脈と突き合わせずに転記する**ことが問題という点です。そこで検出条件は「推奨を示す特徴的なフレーズがある ＋ 文脈を示す語句がない」という形に落とし込みました。

# Stop hookによる機械検出

## 仕組み

Claude Codeのhookは、特定のタイミングで任意のコマンドを実行できる仕組みです。中でも**Stop hook**は、AIが応答を終了するたびに起動し、標準入力から `transcript_path`（会話ログのパス）などを受け取れます。フローは次のとおりです。

1. stdinのJSONから `transcript_path` を取り出す
2. 会話ログ（JSONL）から直近のアシスタント発言を抽出する
3. 推奨を示すパターン（正規表現）にマッチしたら警告する
4. ただし「このプロジェクトでは」等の文脈語句があれば除外する

## 実装例（Python）

```python
#!/usr/bin/env python3
"""Stop hook: テンプレート由来の推奨の無批判転記を検出する"""
import json, re, sys

PATTERNS = [
    r"テンプレートでは.{0,20}推奨",
    r"一般的に推奨され",
    r"公式(にも)?推奨",
]
EXCLUDES = [r"このプロジェクトでは", r"うちの運用では", r"ただし今回は"]

def main():
    payload = json.load(sys.stdin)
    last_text = ""
    with open(payload["transcript_path"], encoding="utf-8") as f:
        for line in f:
            try:
                entry = json.loads(line)
            except json.JSONDecodeError:
                continue
            if entry.get("type") == "assistant":
                blocks = entry.get("message", {}).get("content", [])
                last_text = "\n".join(
                    b.get("text", "") for b in blocks if b.get("type") == "text"
                )

    # 文脈付きの言及ならセーフとみなす
    if any(re.search(p, last_text) for p in EXCLUDES):
        sys.exit(0)

    hits = [p for p in PATTERNS if re.search(p, last_text)]
    if hits:
        print(
            "⚠ テンプレートの推奨を無批判に転記している可能性があります: "
            + ", ".join(hits)
            + " / 出典と自分のプロジェクトの文脈を確認してください",
            file=sys.stderr,
        )
        sys.exit(2)  # exit 2 で stderr がAIにフィードバックされる

if __name__ == "__main__":
    main()
```

settings.jsonへの登録はこうです。

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python3 /path/to/check_template_recommended.py"
          }
        ]
      }
    ]
  }
}
```

`exit 2` で終了するとAIの応答は差し戻され、**stderrの内容がAI自身に見えます**。「根拠を確認して再考させる」という挙動がこれだけで作れます。

# 運用で学んだこと

**（1）差し戻し理由は必ずstderrへ。** 最初の版では検出理由をstdoutに出していました。すると本番で初めて発火したとき、AIは「何が悪かったのか」を受け取れず、同じ回答を繰り返しました。ブロック系のフックで理由を伝えるならstderr一択です。

**（2）誤検出は「除外ワード」で段階的に潰す。** 「〜も推奨」「〜は推奨」のような助詞の揺れは想定より多く、誤検出のたびにパターンと除外語を足し、テストケースを10件超まで増やしました。一発で正解する設計は諦めて、レビュー→改訂のサイクルで磨くのが現実的です。

**（3）自分の過去の失敗でテストする。** パターンを書いたら、実際に自分がAIの提案を鵜呑みにした過去のコミット（自虐を込めて「自害ケース」と呼んでいます）で検出できるか確認しました。手元の5ケースすべてを検出できて初めて導入と判断しました。作った本人の失敗を検出できないなら、それは飾りに過ぎません。

# おわりに

「CLAUDE.mdにルールを書く」のはAIへの**教育**であり、hookは**検疫**です。教育だけでは、AIがテンプレ推奨を流し込むのを確実には止められません。推奨の無批判転記のような「レビューのセンスが要る項目」こそ、特徴的なフレーズの機械検出に落とし込み、人間のレビュー力を本質的な議論に割く――これが筆者の考えるAI駆動開発の衛生管理術です。
