## はじめに

公務員からIT業界に転職して数年、いまはClaude Codeを業務に組み込んで使っています。転職して最初に身につけた教訓は「手作業の定期実行は、必ず人間が忘れる」というものでした。そこから、転載記事の効果測定やキーワードの再生成といった定型作業を、Claude Codeの定期処理（cron形式で登録できるジョブ）へ少しずつ寄せていきました。気づけば20件の定期処理が毎日回る状態になっていました。

ところがある朝、登録したはずの20件が**丸ごと消えていた**のです。

この記事では、次の3点をまとめます。

1. なぜ消えたのか（実測による切り分け）
2. 更新周期をどう決めたか（TDDによる調整）
3. 消えても運用が続く設計（台帳・fail-closed・復旧）

cronや定期実行の運用に興味がある方、特に「設定したはずのジョブがいつの間にか消えていた」経験のある方の参考になれば嬉しいです。

## 1. 20件が消えた — 実測で見つけた「約5日の寿命」

まず現象を整理しました。

- OS側のcrontabは生きている（`crontab -l` で確認できる）
- 消えたのはClaude Code側にdurable（永続）登録したジョブのほう
- 消えたジョブの「最終登録日時」を並べると、どれも**約5日前**だった

ここから「durable登録には暗黙の有効期限（TTL：Time To Live、いわば寿命）があり、更新されなければ約5日で失効する」という仮説が立ちました。ドキュメントに明記された数字ではなかったため、実際に登録と失効を繰り返して自分の環境で実測し、仮説を確定させました。

ここで公務員時代の経験が効きました。役所の届出には有効期限があり、更新申請を忘れると効力を失います。つまり**期限付きの登録は「失効するのが当たり前」**で、論点は「失効するかどうか」ではなく「更新を仕組み化できるか」です。犯人探しではなく、更新サイクルの設計に早々に切り替えました。

## 2. TDDで更新周期を決める — 「5日で消える」なら「3日で更新」

方針が決まったので、まず「再登録が必要か」を判定するロジックをPythonの関数として切り出し、テストから書きました。

```python
from datetime import datetime, timedelta

REFRESH_THRESHOLD_DAYS = 3  # 失効(約5日)より短く設定

def needs_renewal(last_renewed_at: datetime, now: datetime) -> bool:
    """前回の再登録から閾値日数を過ぎたらTrueを返す"""
    return (now - last_renewed_at) >= timedelta(days=REFRESH_THRESHOLD_DAYS)
```

境界値のテストはこうです。

```python
from datetime import datetime, timedelta

def test_境界日ちょうどは更新要():
    base = datetime(2026, 10, 1)
    assert needs_renewal(base, base + timedelta(days=3)) is True

def test_境界の1秒前は更新不要():
    base = datetime(2026, 10, 1)
    assert needs_renewal(base, base + timedelta(days=3, seconds=-1)) is False
```

最初の設定は「閾値5日・再実行間隔6日」でした。しかしこれでは、失効まで5日のジョブを6日後に更新することになり、**必ず間に合わない**。実測値を踏まえ、閾値を5→3日、再登録間隔を6日→3日に改めました。3日周期なら、たとえ1回分の更新漏れが起きても、次のサイクルで失効前に間に合う猶予が生まれます。

「境界が3日である」ことをテストで釘付けにしたのが効き目です。将来（未来の自分を含む）誰かがこの数字を変えたくなったとき、テストが失敗して設計意図を思い出せます。この判定を含む再登録処理まわりは、テストが全て緑になるまで書き上げてから本番に載せました。

## 3. 消えても困らない仕組み — 台帳・fail-closed・復旧

更新の自動化だけでは「消える」リスクはゼロになりません。そこで「消えても数分で戻る」状態を目指して、4つの部品を入れました。

**（1）台帳との差分検知**
「あるべき定期処理」の定義はすべて、自分のGitリポジトリ上の台帳（定義ファイル）に記載し、実環境と毎晩突き合わせます。台帳にあって実体にないジョブは「失効」と判定して再登録し、逆に台帳にないジョブは削除候補にします。**台帳が正、実体は従**という一方向の関係を保つのが要点です。

**（2）fail-closedな適用**
再登録スクリプトは、生成した定義の構文検証が通らなければ中途半端に適用せず、新規ファイルを破棄して既存設定を一切変更しません。検証できないときは「閉じる」、つまり安全側（現状維持）へ倒すのがfail-closedという考え方です。壊れた定義のせいでcron全体が止まる事故を防げます。

**（3）排他制御と実行ログ**
月次バッチと手動実行が同時に走らないよう、`flock` による排他ロックを入れたほか、「当日すでに成功したか」を示すスタンプと実行ログを残します。「動いているはず」ではなく「ログで成功を証明する」運用です。

**（4）バックアップと復旧**
crontabは日次でバックアップし、自動コミットされるようにしています。万一また全滅しても、台帳から全量を再登録するスクリプトが1本あるので、数分で元の状態に戻せます。

## おわりに

学びを1行でまとめると、**「消える」が仕様であるなら、失効を前提に設計する**、です。

- 有効期限のある登録は必ず失効する（公務員の届出管理と同じ）
- 失効周期は実測で確定し、更新周期は境界値テストで釘付けにする
- 台帳・fail-closed・実行ログ・バックアップで「消えても戻る」状態を作る

定期処理が黙って消える不安は、原因の追及だけで終わらせず「失効を見越した再登録と復旧のセット」に落とし込むことで解消できます。同じような現象に遭遇した方の一助になれば幸いです。
