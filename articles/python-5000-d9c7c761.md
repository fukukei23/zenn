# はじめに

機能追加を重ねるうちに、いつのまにか処理が遅くなっていた——そんな経験はないでしょうか。私が開発しているCI実行ハーネス「NexusCore」でも、定題実行ラッパーにガードレールやウォッチドッグを次々と足していくうちに「履歴データが大きくなったとき、本当に大丈夫か？」という不安が出てきました。

そこで導入したのが**劣化スモークテスト**です。本記事では、5000行の履歴データを読み込み＋ウォッチドッグ処理する工程が2秒未満で完走することをCIで保証する仕組みを、実装コード付きで紹介します。

# 劣化スモークテストとは

## 「本格ベンチマーク」と「何もしない」の中間

性能テストと聞くと、統計処理付きの本格ベンチマークを想像しがちです。しかし毎回のCIで回すには重すぎますし、かといって何もしなければ性能劣化は静かに進行します。

劣化スモークテストはその中間に位置します。「スモークテスト」は火災報知器の点検になぞらえた「火を吹いていないか」を確認する最低限のテストという意味です。そして「劣化」は、絶対値の最適化ではなく**「以前と比べて明らかに壊れていないか」の検出**を指します。つまり「速くすること」ではなく「壊れたらわかること」を目指します。

## 閾値の決め方：100倍の余裕

今回の実測値は0.018秒、閾値は2秒。約100倍の余裕があります。これは意図的な設計です。

CI実行環境のCPU負荷はブレます。ギリギリの閾値では誤検出が頻発し、やがて「赤は無視する」文化が生まれます。100倍の余裕があれば環境ノイズでは落ちず、処理が二重ループに落ちたり同期IOを大量に積むような「本物の劣化」だけを確実に捕まえられます。

## なぜ5000行なのか

テストは平均ケースではなく**想定最悪ケース**で行うべきです。このハーネスは恒久履歴を溜め込む設計のため、運用が長くなるほど履歴は増えます。5000行は「長く運用した状態」を模した数字です。小さいデータで测试しても、本番で破綻する劣化は見逃されます。

# pytestでの実装

記事用に簡略化したコードがこちらです。

```python
import time
import pytest

MAX_HISTORY_LINES = 5000
THRESHOLD_SECONDS = 2.0


def make_history(lines: int = MAX_HISTORY_LINES) -> list[str]:
    """運用で積み上がることを想定した最悪サイズの履歴を生成する"""
    return [
        f"[2026-09-09T00:{i // 60:02d}:{i % 60:02d}] "
        f"turn={i} status=ok tokens={100 + i}"
        for i in range(lines)
    ]


def run_degradation_smoke(harness) -> float:
    """5000行履歴のload+watchdog所要時間を測定し、閾値超過なら例外を投げる"""
    history = make_history()

    start = time.perf_counter()
    harness.load_history(history)
    harness.run_watchdog(history)
    elapsed = time.perf_counter() - start

    assert elapsed < THRESHOLD_SECONDS, (
        f"性能劣化の疑い: load+watchdog が {elapsed:.3f}s"
        f"（閾値 {THRESHOLD_SECONDS}s）"
    )
    return elapsed


def test_degradation_smoke(harness):
    elapsed = run_degradation_smoke(harness)
    print(f"smoke elapsed: {elapsed:.3f}s")  # 実測は0.018s程度
```

ポイントは3つです。

1. **`time.perf_counter()` を使う**： `time.time()` より解像度が高く、システム時刻変更の影響を受けません
2. **失敗時に実測値を出す**： 「閾値超過」だけでは原因調査の糸口がありません。何秒だったかをメッセージに含めます
3. **モックではなく本物のコードパスを通す**： 実際のロード関数とウォッチドッグを呼びます

## テスト自身を検証する（ミューテーションの発想）

「このテスト、本当に劣化を検出できるのか？」を確認するため、わざと遅いコードを注入してテストが赤になることを確かめました。

```python
def test_smoke_detects_injected_slowness(harness, monkeypatch):
    """人工的な劣化を注入し、スモークが検出できることを保証する"""

    def slow_load(history):
        for _ in history:
            time.sleep(0.001)  # 5000行 × 1ms ≈ 5秒
        return history

    monkeypatch.setattr(harness, "load_history", slow_load)

    with pytest.raises(AssertionError, match="性能劣化"):
        run_degradation_smoke(harness)
```

1行あたり1msのsleepで全体が約5秒になり、テストは期待どおり失敗します。「劣化したら検出できる」ことまで保証されて、初めてスモークテストとして信用できます。実際のリポジトリでは、同様の変異パターンを10種類用意し、すべて検出（全キル）できることを確認しました。

# CIでの運用と公的システムへの応用

## タイムアウト設計との整合

このハーネス自体にウォッチドッグ（一定時間で処理を打ち切る仕組み）があります。スモークテストの閾値2秒は、このウォッチドッグのタイムアウト値と整合させています。「処理系が健全ならウォッチドッグに引っかかる前に完走する」という不変条件を、テストが守っている形です。

## 公的システムで特に効く理由

公的システムのような長期運用されるシステムでは、

- 申請データや履歴が年々積み上がる
- 法改正対応などで機能追加が絶えず行われる

という条件が重なります。この2つが複合すると「リリース時の性能試験では問題なかったのに、運用3年目で急に遅くなった」という事態が起きます。データ量を固定した劣化スモークテストをCIに組み込んでおけば、機能追加のPR段階で「この変更は履歴が大きいときに破綻する」と検出できます。数十ミリ秒で終わるテストなので、CIへの追加コストはほぼゼロです。

:::message
性能試験の代替ではなく補完です。重要なリリース前には本格的な負荷試験を行い、スモークテストは日常の変質検出に徹する、という使い分けが現実的です。
:::

# おわりに

- 劣化スモークテストの目的は「速さの追求」ではなく「壊れたら気づくこと」
- 閾値は実測値の100倍程度の余裕を持たせ、誤検出を防ぐ
- 平均ケースではなく最悪ケースのデータ量（今回は5000行）でテストする
- ミューテーションの発想で「テストが劣化を検出できること」自体を検証する

性能劣化は静かに進行し、気づいたときには「どの変更のせいで遅くなったのか」の特定が困難になっていることも多いです。数十行のスモークテストを今日入れておくだけで、その不安をCIが肩代わりしてくれます。この記事がその一歩の後押しになれば幸いです。
